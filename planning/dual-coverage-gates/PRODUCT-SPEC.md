# Dual Coverage Gates — Product Specification

**Date**: 2026-08-12
**Session**: dual-coverage-gates
**Status**: Draft

## Overview

Add a dual coverage gate — feature coverage AND line coverage, each gated at ≥90% — to Shipwright's own test-readiness pipeline (test-inventory → test-design → test-migration → test-roadmap → test-fix). Today the pipeline enforces a single flat 80% line+function floor with no feature-level signal and no computed readiness verdict; "ready" is only implied by task-store tickets reaching `done`. This work makes readiness a first-class, machine-checkable verdict, without reintroducing the file-level criticality→CI mapping the pipeline deliberately avoids today.

## Problem Statement

The pipeline's coverage floor is tier-agnostic by design (to avoid a decaying criticality-to-CI mapping), but that means it has no way to tell "95% lines, but the checkout flow has zero tests" from genuine readiness. There is also no computed `coverage_gate` verdict anywhere — a human or agent has to infer readiness from task-store ticket status, with no single source of truth for "is this repo actually ready."

## Users & Context

Primary consumer: **the autonomous agent itself**. The test-readiness pipeline's stated purpose is to "audit whether a codebase's tests can be trusted by an autonomous agent" — `coverage_gate.verdict` is what the agent reads to decide whether to keep filing test-fix tasks or report a repo READY. Secondary surface: **`docs/testing.md`**, generated by `/research-docs` digesting `docs/test-readiness/` output, read by humans who want a quick view of test posture without running the pipeline themselves.

## Features

### Feature 1: Feature-Coverage Matrix (test-inventory extension)

**Priority**: High (foundational — everything else depends on this existing)
**Description**: Extends `test-inventory` (Phase 1) to group related code units into "features" (one level coarser than a file/function) and compute a feature-level coverage percentage, without reintroducing a maintained per-file criticality→CI mapping.

**User Stories**:
- As the autonomous agent, I want to know whether every user-facing feature has at least one test, not just whether enough individual lines are covered, so that a repo isn't declared ready while an entire capability has zero test coverage.

**Requirements**:
- Feature boundaries are inferred automatically (directory structure, route prefixes, shared entry points) — no manual authoring step, no maintained mapping file.
- Each feature is tagged with an importance label (revenue-path / security-path / core / auxiliary) for **prioritization only** — no importance tag excludes a feature from the coverage denominator (cosmetic-tier exclusion was considered and explicitly rejected).
- Ambiguous groupings (e.g. a shared utility that could belong to multiple features) are flagged for visibility, following the same pattern `test-inventory` already uses for ambiguous items today — not blocking, not requiring human sign-off.
- A feature's required test layer is the **highest** layer among its member code units' prescribed layers (from test-design) — not the full union of layers.
- A feature counts as "covered" only if it has ≥1 test at that required layer, and that test isn't itself flagged for deletion/rebuild by `test-migration` (Phase 3).
- `feature_coverage_pct = covered_features / total_features × 100` — every non-deleted feature counts in the denominator, full stop.
- Gate: ≥90%.

**Acceptance Criteria**:
- [ ] `test-inventory` output includes a features grouping section, with every code unit assigned to exactly one feature and each feature tagged with an importance label
- [ ] Ambiguous feature groupings are flagged in the output the same way `test-inventory` flags ambiguous items today (visible, non-blocking)
- [ ] `feature_coverage_pct` is computed as `covered_features / total_features × 100` with no exclusion category of any kind
- [ ] Each feature's required test layer is documented as the highest layer among its member units' prescribed layers

**Technical Considerations**: Must not introduce a maintained per-file criticality→CI mapping (hard constraint — this is a coarser, separate structure). No JSON schema exists in `test-inventory.md` today (markdown-only); the feature grouping needs a machine-parseable representation for downstream phases (test-migration, test-roadmap) to consume — likely a structured section within the existing markdown output, matching the format `test-migration`'s five-bucket reconciliation already uses.

**Source Map**:
- `plugins/shipwright/skills/test-inventory/SKILL.md` — add feature-grouping step
- `plugins/shipwright/assets/templates/` — inventory output template, if one exists for Phase 1
- `.claude/shipwright/test-readiness-decisions.md` — registry pattern to mirror for ambiguous-grouping visibility (read-only reference, not modified by this feature)

**Testing Strategy**: Layer: unit — grouping/heuristic logic and `feature_coverage_pct` computation are pure functions over inventory data, no I/O.

### Feature 2: Computed `coverage_gate` Block + Self-Consistency Guard

**Priority**: High (depends on Feature 1 existing; blocks Features 3 and 4's sequencing/ratchet logic)
**Description**: Whichever phase already computes real numbers today (test-migration or test-roadmap) emits a `coverage_gate` block — feature and line percentages, their sources, and a READY/BLOCKED verdict — rendered into `docs/test-readiness/test-readiness-plan.md`. The render step refuses to emit an inconsistent plan.

**User Stories**:
- As the autonomous agent, I want a single computed verdict with named gaps, so I don't have to infer readiness from scattered percentages or task-store ticket counts.

**Requirements**:
- `coverage_gate` block fields: `feature_coverage_pct`, `feature_coverage_source`, `line_coverage_pct`, `line_coverage_source`, `verdict` (READY | BLOCKED), `targets: { feature: 90, line: 90 }`.
- Percentages must come from an actual coverage run or an existing CI artifact — never estimated (verify-before-cite). If a real number isn't available, the field is `null`, not a guess.
- `verdict` is READY only when both percentages are ≥90%; otherwise BLOCKED, naming the specific gap(s) (e.g. "line coverage 84% < 90%").
- Per-repo coverage tool (JaCoCo/coverage.py/c8-nyc/go cover) is detected and recorded in `test-system.md`'s existing CI pipeline shape section (Phase 2), the same way CI pipeline shape is already recorded per repo — this is what Feature 2's computation step reads to know how to source `line_coverage_pct`.
- The step that renders `test-readiness-plan.md` refuses to emit the plan if the `coverage_gate` block is missing, or if `verdict` contradicts the reported percentages (a correctness backstop, not new user-facing behavior).

**Acceptance Criteria**:
- [ ] `coverage_gate` block renders in `test-readiness-plan.md` with all six fields present
- [ ] Percentages are sourced from an actual coverage run or CI artifact; the source is cited in `feature_coverage_source`/`line_coverage_source`; no guessed numbers ever appear
- [ ] `verdict` is READY only when both percentages are ≥90%, BLOCKED otherwise, with the response naming which gate(s) failed and by how much
- [ ] The render step throws/refuses rather than writing the plan if `coverage_gate` is missing or self-contradictory
- [ ] Per-repo coverage tool is detected and recorded in `test-system.md` alongside existing CI pipeline shape data

**Technical Considerations**: `test-migration` doesn't compute coverage percentages today — only speed-budget wall-clock measurements. This is new computation, not an extension of existing logic. `test-roadmap` writes `test-readiness-plan.md` from a plugin template (`${CLAUDE_PLUGIN_ROOT}/assets/templates/test-readiness-plan.md.tmpl`); the template needs a `coverage_gate` section added.

**Source Map**:
- `plugins/shipwright/skills/test-migration/SKILL.md` or `plugins/shipwright/skills/test-roadmap/SKILL.md` — whichever owns the computation (needs a decision during plan-session about which phase this belongs to)
- `plugins/shipwright/assets/templates/test-readiness-plan.md.tmpl` — add `coverage_gate` block + guard
- `docs/test-readiness/test-system.md` — add coverage-tool field to CI pipeline shape section

**Testing Strategy**: Layer: unit — verdict computation and the self-consistency guard are pure logic over already-sourced numbers. Layer: integration — reading real lcov/JaCoCo/etc. artifacts to populate the percentages requires exercising the actual parser against fixture files.

### Feature 3: Line-Coverage Floor Raise, Multi-Tool Support, and Sequencing Rule

**Priority**: Medium (depends on Feature 2's coverage-tool detection existing)
**Description**: Raises the flat line-coverage floor from 80% to 90%, extends `scripts/check-coverage.ts`'s single-tool (Bun/lcov) logic to support JaCoCo (XML), coverage.py, c8/nyc, and go cover, and adds a sequencing/anti-gaming rule to `test-roadmap`/`test-fix` so feature gaps are always closed before line-coverage filler tasks.

**User Stories**:
- As the autonomous agent, I want feature-coverage gaps to be sequenced ahead of line-coverage filler work, so a repo at 95% lines but 60% features isn't treated as nearly done.
- As a repo owner on a non-Bun repo, I want the line-coverage gate to work against my language's native coverage tool, not just lcov.

**Requirements**:
- `scripts/check-coverage.ts`'s `THRESHOLD_LINES`/`THRESHOLD_FUNCTIONS` raised from 80 to 90 (Bun/lcov path, Shipwright's own repo).
- New parser adapters for JaCoCo XML, coverage.py, c8/nyc, and go cover output formats, selected per repo based on the tool recorded in `test-system.md` (Feature 2). All four tools are in scope now, not deferred to follow-on tasks.
- The gate stays a single flat number per repo — no per-file, no per-tier.
- `test-roadmap`/`test-fix`: when both a feature gap and a line gap exist in the same milestone, feature-coverage-closing tasks are always sequenced before line-coverage filler tasks.
- Anti-gaming rule: a line-coverage task must map to a real feature or a genuine uncovered error path — `test-fix` rejects/flags assertion-free filler tests added just to move the number.

**Acceptance Criteria**:
- [ ] `check-coverage.ts` gates Shipwright's own repo at ≥90% line coverage instead of 80%
- [ ] Coverage parsing correctly extracts line percentages from JaCoCo XML, coverage.py, c8/nyc, and go cover output (verified against a fixture file per tool)
- [ ] `test-roadmap`'s task list sequences feature-coverage-closing tasks ahead of line-coverage filler tasks whenever both gap types exist in the same milestone
- [ ] A line-coverage task emitted by `test-roadmap`/`test-fix` cites the specific feature or uncovered error path it maps to; a task with no such mapping is not emitted

**Technical Considerations**: This is the largest scope item in the PRD — four new parser adapters, not a threshold-constant change. Each tool's output format differs meaningfully (JaCoCo is XML with per-class counters; coverage.py has its own XML/JSON; c8/nyc emits Istanbul-format JSON; go cover uses a custom text profile format) — expect this to be its own build item with per-tool sub-tasks during plan-session, not a single task.

**Source Map**:
- `scripts/check-coverage.ts` — raise threshold, add multi-tool dispatch
- `Taskfile.yml` — `test:coverage` task, if tool selection needs wiring here
- `plugins/shipwright/skills/test-roadmap/SKILL.md` — sequencing rule
- `plugins/shipwright/skills/test-fix/SKILL.md` — anti-gaming rejection rule

**Testing Strategy**: Layer: unit — each parser adapter is pure format-parsing logic, tested against fixture files per tool. Layer: integration — sequencing behavior against a synthetic fixture with both feature and line gaps present.

### Feature 4: CI Ratchet in repo-config

**Priority**: Medium (depends on Feature 2's `coverage_gate` verdict existing; can be built in parallel with Feature 3)
**Description**: A two-stage promotion of the required coverage check in `repo-config`, so raising the floor to 90% doesn't instantly break every repo currently below it.

**User Stories**:
- As a repo owner, I want my PRs blocked from *decreasing* coverage immediately, without being blocked by a hard 90% requirement I haven't had a chance to reach yet.

**Requirements**:
- Stage (a): immediately require that a PR not *decrease* line coverage — wired as a required GitHub status check via the existing `repo-config` branch-protection pairing pattern (CI job lands → dependent task enables it as required).
- Stage (b): once a repo's roadmap actually closes the gap to ≥90% (detected via `coverage_gate.line_coverage_pct >= 90` on a `test-roadmap` re-run), `repo-config` automatically emits a task to promote the required check to a hard ≥90% gate.
- Promotion is automatic — no manual step. This extends the existing 2-stage branch-protection pairing pattern to a 3-stage lifecycle (job lands → never-decrease required → hard-90%-required).

**Acceptance Criteria**:
- [ ] A repo newly onboarded through the pipeline gets a required "coverage must not decrease" check as soon as the coverage CI job lands
- [ ] A repo-config task to promote to a hard ≥90% required check is generated only after `test-roadmap` confirms `line_coverage_pct >= 90` on a re-run
- [ ] The promotion happens without manual intervention — `test-roadmap` emits the task automatically, following the existing repo-config pairing pattern
- [ ] A repo already at ≥90% at onboarding time gets the hard gate directly, without unnecessarily passing through the never-decrease stage first

**Technical Considerations**: Builds directly on `repo-config`'s existing branch-protection pairing pattern (documented in `plugins/shipwright/skills/repo-config/SKILL.md`) — this is an extension of that pattern to a third stage, not a new mechanism.

**Source Map**:
- `plugins/shipwright/skills/repo-config/SKILL.md` — extend branch-protection pairing to 3-stage lifecycle
- `plugins/shipwright/skills/test-roadmap/SKILL.md` — emit the promotion task on re-run when the gap closes

**Testing Strategy**: Layer: integration — branch-protection API calls via an injected GitHub client double, following the existing test pattern for `repo-config`.

## Technical Constraints

- Must NOT reintroduce a maintained per-file criticality→CI mapping — the feature-coverage matrix is a coarser, separate structure (features, not files) and must not collapse back into file-level enforcement.
- This is an evolution of the existing 5-phase pipeline plus the existing `repo-config` and `speed-budgets` contract skills — not a parallel system.
- Applies across every repo the pipeline runs against (`repos/*`), each with a different toolchain — the coverage tool must be detected and recorded per repo the same way `test-design` already records CI pipeline shape.
- Both gates are ≥90% flat numbers — not per-file, not per-tier, not a range.
- `scripts/check-coverage.ts`'s lcov mechanism is preserved for Shipwright's own repo; other tools are additive parser adapters, not a replacement.

## Scope

**In Scope**:
- Automatic feature grouping and `feature_coverage_pct` computation in `test-inventory`
- `coverage_gate` computation, rendering, and self-consistency guard
- Line-coverage floor raise to 90% + multi-tool parser support (JaCoCo, coverage.py, c8/nyc, go cover)
- Feature-gap-before-line-gap sequencing rule + anti-gaming rejection in `test-roadmap`/`test-fix`
- Two-stage CI ratchet in `repo-config`

**Out of Scope**:
- Retroactive rewrite of already-generated `docs/test-readiness/` output for repos under the old flat-80% design — this only applies when a repo is re-run through the pipeline
- Any per-file or per-tier CI enforcement, in any form
- New task-store schema fields beyond what `test-fix` already supports (dependencies, priority, hitl, acceptanceCriteria)
- A cosmetic-tier exclusion from the coverage denominator — considered and explicitly rejected during this session

## Priorities & Sequence

Feature 1 (feature-coverage matrix) must land first — Features 2, 3, and 4 all depend on feature-level data existing. Feature 2 (`coverage_gate` computation + guard) must land before Feature 4 (CI ratchet), since the ratchet's promotion logic reads `coverage_gate.line_coverage_pct`. Features 3 and 4 can be built in parallel once Feature 2 lands — Feature 3's sequencing rule and Feature 4's ratchet don't depend on each other, only on Feature 2's verdict/detection groundwork.

## Resolved Decisions

- **Cosmetic-tier exclusion**: Dropped entirely. Every non-deleted feature counts toward `feature_coverage_pct`'s denominator. Importance tags (revenue-path/security-path/core/auxiliary) remain as prioritization metadata only, never excluded. — Rationale: "a feature is a feature and should be covered by a test"; also removes a gaming vector where features could be mistagged to shrink the denominator.
- **Feature required-layer definition**: The highest layer among a feature's member code units' prescribed layers, not the full union. — Rationale: simpler; explicit preference over requiring coverage at every member unit's layer.
- **Feature grouping mechanism**: Fully automatic, inferred from directory/route/entry-point heuristics — no human-confirm step. — Rationale: matches the pipeline's existing read-only/automated Phase 1-4 design; avoids reintroducing a maintained mapping.
- **Ambiguous grouping handling**: Flagged for visibility using the same pattern `test-inventory` already uses for ambiguous items — not blocking. — Rationale: catches misgrouping risk (e.g. shared utilities) without requiring a blocking human-approval gate.
- **Multi-tool coverage support scope**: JaCoCo (XML), coverage.py, c8/nyc, and go cover are all in scope for this PRD, not deferred to follow-on work. — Rationale: explicit requirement — the gate applies across every repo the pipeline runs against, each with a different toolchain.
- **Coverage-tool detection storage**: Recorded in `test-system.md`'s existing CI pipeline shape section (Phase 2 output), one field alongside what's already recorded per repo. — Rationale: mirrors the existing pattern for CI pipeline shape; no new artifact needed.
- **CI ratchet promotion mechanism**: Automatic — `test-roadmap` detects `coverage_gate.line_coverage_pct >= 90` on a re-run and emits the promotion task itself, following the existing `repo-config` branch-protection pairing pattern (job lands → dependent task enables it). — Rationale: consistent with the existing pairing pattern; avoids manual toil.
- **Retroactive scope**: Applies only when a repo is re-run through the pipeline (`test-inventory` → `test-roadmap`); no backfill migration for existing `docs/test-readiness/` output under the old design. — Rationale: matches the plugin's existing idempotency/no-cross-skill-dependency design constitution.
- **Primary user**: The autonomous agent itself is the primary consumer of `coverage_gate.verdict`, deciding whether to keep filing test-fix tasks; `docs/testing.md` (via `/research-docs` digestion) is the secondary human-facing surface. — Rationale: matches the pipeline's stated purpose of auditing test trustworthiness for an autonomous agent.

## Success Criteria

- A full pipeline re-run (`test-inventory` → `test-design` → `test-migration` → `test-roadmap`) on Shipwright's own repo produces a `coverage_gate` block in `test-readiness-plan.md` with real (not guessed) percentages and correctly cited sources.
- `verdict` correctly reports BLOCKED with named gap(s) when either dimension is below 90%, and READY only when both are ≥90%.
- `scripts/check-coverage.ts` enforces the 90% floor on Shipwright's own Bun/lcov path.
- At least one non-Bun repo profile under `repos/*` (e.g. a Python or Go repo) validates that coverage-tool detection and parsing generalize beyond lcov.
- `repo-config` emits the correct two-stage branch-protection tasks: never-decrease immediately for a repo currently below 90%, versus a direct hard-90% gate for a repo already at or above 90% at onboarding.
- `test-roadmap` sequences feature-gap-closing tasks ahead of line-coverage filler tasks against a synthetic fixture containing both gap types.
