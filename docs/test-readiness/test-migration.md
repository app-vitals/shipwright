## Method note

This is the fifth `/test-migration` pass merged to `main` (prior: 2026-07-16, 2026-07-19,
2026-07-21, committed as this file's history shows; two additional passes dated
2026-07-23 and 2026-07-26 exist only on unmerged sibling refresh branches — see Phase 1's
note on that pattern). Rather than re-read all ~249 test files cold, this pass diffed the
current file tree against the 2026-07-21 pass's findings and re-verified each open item
directly, then did a fresh full-suite discovery pass to catch anything the diff approach
would miss:

1. Enumerated every test file via the Phase 2 framework matrix's glob patterns (`bun
   test`'s default discovery for `*.unit.test.ts` / `*.integration.test.ts` /
   `*.smoke.test.ts` / `*.content.test.ts`, plus `site/**/*.spec.ts`, plus
   `{admin,metrics}/e2e/**/*.e2e.ts`).
2. Re-checked every open item from the 2026-07-21 report (1 real net-new gap —
   `mcp-server/src/main.ts`'s fail-closed guard; 1 carried-forward optional item —
   `admin/src/clock.ts`; 0 net-new infra) against the current tree by direct
   file-existence and content checks — not assumed from memory.
3. Cross-referenced Phase 1's "new since the 2026-07-21 inventory" file list (9 new
   non-test source files, centered on the Agent Type manifest system and the
   author-allowlist gate) against the test-file glob to find newly-introduced coverage
   gaps, and directly read the two integration/unit test files for
   `agent-type-manifest-loader.ts` to confirm the specific fallback/hard-failure
   contracts flagged in this pass's own Phase 2 doc are actually exercised as named test
   cases, not incidentally covered.
4. Re-ran the isolation-contract grep sweep (`mock.module(`, `global.fetch =`,
   `global.console =`, `DATABASE_URL` inside `*.unit.test.ts`) across the full current
   suite, not just the delta, to catch any regression introduced by unrelated PRs since
   the last pass.
5. Confirmed `.github/PULL_REQUEST_TEMPLATE.md` and `bunfig.toml`'s `pathIgnorePatterns`
   directly rather than trusting the prior doc's snapshot.
6. Read `mcp-server/src/main.smoke.test.ts` in full to confirm the fail-closed guard
   flagged as a real, unresolved gap at the 2026-07-21 pass is now actually exercised —
   via a real child-process spawn with the token env var explicitly absent, respecting
   the repo's no-`process.env`-mutation-in-shared-test-process isolation rule (documented
   in the test file's own header comment).

**Speed measurement: not re-run this pass**, same reasoning as all four prior passes — no
local Postgres in this sandbox (`DATABASE_URL_SHIPWRIGHT_*` unset), so a `bun test` run here
would silently skip every DB-backed integration test and produce misleading timings.
Static review (line counts, import/mock shape) was used instead; no evidence found of any
test breaching a hard cap. A real per-layer measurement continues to exist at
`docs/test-readiness/speed-baseline.md` on `main` (unchanged since 2026-07-15, already
cross-referenced into `test-system.md`'s Speed budgets section since the 2026-07-19 pass
per T-067/PR #1930 — no further correction needed this cycle).

**Note on the SKILL's carried-forward-measurement-item rule:** this is not the trigger
case the SKILL's Failure-modes section warns about — that rule targets a load-bearing
measurement that has *never* been taken and is silently carried forward unaddressed
across cycles. Here, a real, `time`-wrapped measurement was already taken once
(`speed-baseline.md`, committed 2026-07-15, PR #1580) and is correctly cross-referenced;
what's carried forward each pass is only this specific sandbox's inability to *re-measure*
(no local Postgres), which is a sandbox constraint on re-verification, not an unaddressed
design gap. No Milestone-1 escalation is warranted from this alone. See
`project_shipwright_metrics_full_suite_flake` and `project_shipwright_admin_full_suite_flake`
in memory for the two known pre-existing full-suite flakes (unrelated to layer/speed, not
relevant to this audit).
