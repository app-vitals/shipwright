### 2. Service-boundary code

Every workspace has a Prisma-backed service layer (task-store: `task-service.ts`/`pull-request-service.ts`/`token-service.ts`; chat: `message-service.ts`/`thread-service.ts`/`token-service.ts`; admin: `agent-envs.ts`/`agent-cron-jobs.ts`/`agent-chat-tokens.ts`/`agent-work-queue.ts`/etc.) plus internal HTTP clients (`metrics/src/lib/task-store-client.ts`, `agent/src/shipwright-*-client.ts`, `admin/src/*-provisioning-client.ts`). The agent's `check-*.ts` / `loop-orchestrator.ts` family is a distinctive service-boundary cluster: it composes GitHub API reads with task-store writes and is the operational core of the dev-task/review/patch/deploy loop — ranked critical.

This cycle's changes concentrate in two places:

1. **`agent/src/check-review.ts` (RCS-1.1/1.2/1.3)** — the staged-review skip guard (`record.staged === true && record.commitSha === pr.headRefOid`) now reads a new, review-pipeline-exclusive `reviewedCommitSha` field instead of the shared `commitSha` field. `commitSha` is also advanced by `PullRequestService.patch()`/`claim()`/`deploy` for unrelated multi-phase bookkeeping — keying the guard on it meant a `patch()`-driven bump (e.g. after a CI-fix cycle) could make a stale, never-re-reviewed staged review look "already reviewed at this head." `reviewedCommitSha` is written exclusively by `review.md`, closing that masking window. This is a correctness fix to an existing service-boundary module, not a new category-2 surface.
2. **`agent/src/pr-state-reconciler.ts` (RDG-1.1)** — `reconcilePrOpenTask()`'s DIRECT path (`task.pr` already set) previously advanced a task straight to "merged" on GitHub confirming MERGED, with no bundle-mate check — unlike the branch-fallback path below it, which already enforced a bundle-mate-headcount (BBR-1.1) + `startedAt` (RCP-1.1) precondition. This let a trailing sibling task on a multi-task branch ride a bundle-mate's real merge to "merged" via its own `task.pr` field alone, without its own `startedAt` ever being set — confirmed live on IC-1.2/1.3/1.4, DPF-2.2, PW-1.2, SBA-1.2 (all reset to `pending` as a manual data fix at the time). RDG-1.1 applies the same precondition to the direct path, gating only the merge-advance (the `ghViewPr` call itself always runs).

Also new this cycle: **`agent/src/browser.ts`** (`launchBrowser` — wraps `chromium.launch()` with `--no-sandbox`/`--disable-setuid-sandbox` for the pod's `runAsNonRoot` securityContext). Classified category 2 (spawns and drives a real out-of-process browser) rather than category 5, since Chromium here is a bundled runtime dependency the agent controls directly (installed into the image at build time), not a third-party *service* we call over the network — closer in spirit to a file-system/subprocess wrapper than an external API client. `scripts/hitl.ts` gained meaningful new service-boundary logic this cycle: an auto-clone preflight (`gh repo clone` for any `SHIPWRIGHT_HITL_REPOS` entry not already present) and `agent-policy.md` template seeding, both process-spawning/file-I/O — stays category 2, ranked high given it now directly affects whether a fresh local HITL bootstrap succeeds unattended.

`admin/src/agents.ts` / `agents-api.ts` and the K8s/manifest cluster are unchanged this cycle.
