**CLAUDE.md layer-structure declaration:** the root CLAUDE.md's `## Test conventions` section declares five concrete layer names via filename suffix, used verbatim below instead of the rubric's generic unit/integration/smoke/E2E labels:

| Suffix | Layer | Covers |
|---|---|---|
| `*.unit.test.ts` | unit | pure logic, no I/O |
| `*.integration.test.ts` | integration | real dependency behavior via recorded fixtures / injected doubles |
| `*.smoke.test.ts` | smoke | HTTP route contracts — in-process `app.request()` (real `Bun.serve()` boot only when there's no Hono app-factory seam) |
| `*.spec.ts` / `*.e2e.ts` | e2e | real-browser Playwright (`site/` uses `*.spec.ts`; `admin/e2e/` uses `*.e2e.ts`) |
| `*.content.test.ts` | content | markdown/prompt-content assertions (commands, skills, agent prompts) — no I/O boundary, not one of the four canonical layers but a first-class fifth layer in this repo |

## Per-category detail

### 1. Pure business logic

The largest category by file count. Concentrated in `lib/` (shared cross-service helpers imported by `agent/`, `admin/`, `metrics/`, `task-store/`), decision/classification logic (`agent/src/work-selector.ts`, `task-store/src/ready.ts`/`blocked-by.ts`/`statuses.ts`, `plugins/shipwright/scripts/classify_test_layer.ts`/`check-helpers.ts`'s `isCleanApproveBody`/`check-patch.ts`'s `isSupersededBySelfReview`), mutable-box refs (`agent/src/agent-repos-ref.ts`, `loop-jobs-ref.ts`, `review-author-allowlist-ref.ts`, `patch-author-allowlist-ref.ts`, `agent-slack-membership-ref.ts`), pure wire-object builders (`admin/src/agent-manifest.ts`, `dev-auth-guard.ts`, `admin/src/agent-type-registry.ts`'s schema/JSON-Schema builder — **new this cycle**), crypto helpers treated as pure (`agent/src/crypto.ts`, `admin/src/crypto.ts`/`token-crypto.ts` — deterministic given key/IV, `node:crypto` is in-process not a boundary), and parsing/validation utilities (`scripts/check-coverage.ts` family, `brand/brand-lint.ts`/`build-brand-css.ts`, `admin/src/attachment-validation.ts`, `agent/src/piper-voice.ts`). `scripts/hitl.ts`'s planner functions (`buildHitlConfig`, `buildPreflightSteps`, `buildServiceSpecs`) are pure command/config builders per `test-readiness-decisions.md`. `task-store/src/claim-ttl-buffer-check.ts` and `webhook-timeout-buffer-check.ts` are opt-in startup sanity checks, pure given their injected env-value inputs.

These are the repo's dominant unit-test surface (`*.unit.test.ts` siblings observed for essentially every row in this category during enumeration, not individually read in full).

### 2. Service-boundary code

Every workspace has a Prisma-backed service layer (task-store: `task-service.ts`/`pull-request-service.ts`/`token-service.ts`; chat: `message-service.ts`/`thread-service.ts`/`token-service.ts`; admin: `agent-envs.ts`/`agent-cron-jobs.ts`/`agent-chat-tokens.ts`/`agent-work-queue.ts`/etc.) plus internal HTTP clients (`metrics/src/lib/task-store-client.ts`, `agent/src/shipwright-*-client.ts`, `admin/src/*-provisioning-client.ts`). The agent's `check-*.ts`/`loop-orchestrator.ts` family is a distinctive service-boundary cluster: it composes GitHub API reads with task-store writes and is the operational core of the dev-task/review/patch/deploy loop — ranked critical. Every service's `PrismaClient` construction is extracted into its own `prisma-client.ts` (admin, task-store, chat). `scripts/generate-agent-type-schema.ts` (new this cycle) is a thin file-I/O wrapper around `admin/src/agent-type-registry.ts`'s pure builder, folded into the existing dev-tooling codegen composite row.

### 3. HTTP routes / public API

Every service (metrics, admin, task-store, chat, mcp-server) exposes a Hono app factory with a route table documented in its own header comment. `agent/src/cron-handler.ts` and `agent/src/slack.ts` are treated as route-equivalent (own a wire contract with an external caller, even though not URL-routed). Canonical layer is smoke throughout, consistent with the CLAUDE.md convention (`*.smoke.test.ts` — in-process `app.request()`). `.github/workflows/check-chart-drift.yml` is flagged as route-*equivalent* rather than a literal HTTP route (see Ambiguous).

### 4. Error / failure paths

Thin category — most error handling is folded into the service/route layer rather than living in dedicated retry/circuit-breaker modules (no queue/retry infrastructure observed). Distinct logic-only error modules: `metrics/src/lib/errors.ts`, `admin/src/errors.ts`, `task-store/src/errors.ts`, `chat/src/errors.ts` (typed HTTP error classes — unit), and `agent/src/cutover-validate.ts` (validation gate — unit). `task-store/src/stale-claim-reaper.ts` and `agent/src/pr-state-reconciler.ts` are boundary-involving error/self-heal paths — integration. `agent/src/cron-failure-reporter.ts` is a boundary-involving error path: it catches a thrown cron-tick error, writes an AgentCronRun row via the admin API, and captures to Sentry — ranked high given it is the only thing standing between a swallowed cron crash and operator visibility. `agent/scripts/verify-browser-launch.ts` (environment-capability gate, CI-only, no `bun test` suffix) remains its own edge case (see Ambiguous).

### 6. User journeys

Five top-level product journeys:

1. **dev-task → review → patch → merge/deploy pipeline** — the core product loop. Critical — this is the product. Includes human-invoked `/shipwright:merge` and `/shipwright:unblock` triage sub-steps, both explicitly exempt from the Candidate Selection Contract and never run unattended.
2. **Agent provisioning** — admin creates an Agent record (type-aware manifest resolution via `admin/src/agent-type-registry.ts` + `agent-type-manifest-loader.ts`, seeded repos/tools/plugins/members/allowlists), which cascades through `agent-provisioner.ts` → K8s Deployment/Secret → task-store/chat-service token minting → the agent container boots and reports `/health`. Critical.
3. **Slack chat with an agent** — DM/mention → chat-svc queue → `agent/src/chat-poller.ts`'s poll/claim loop → Claude session → Slack reply, with `chat/src/stall-reaper.ts`'s 300s-stall self-heal path. High.
4. **Marketing site visitor journey** — landing → docs → self-hosted quickstart, covered by `site/`'s existing Playwright `*.spec.ts` suite per CLAUDE.md. High.
5. **Local HITL dev-loop bootstrap** — `task hitl` → auto-clone missing repos → seed `agent-policy.md` → boot task-store + admin locally → poll for ready work → dispatch Claude Code. Medium.

No journey is browser-driven except #4 (plus #2's detail-page rendering step). #1, #3, and #5 are best proven by cross-service integration tests composing recorded fixtures / injected doubles rather than a literal Playwright E2E, since there is no UI for the pipeline or the HITL bootstrap itself — noted as "e2e/smoke-composed" or "integration-composed" in the summary table to flag that the canonical E2E *tooling* (browser automation) doesn't apply, but the *layer* (multi-step, multi-process state) still does.
