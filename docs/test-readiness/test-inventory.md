## Stack profile

- **Language(s):** TypeScript (Bun runtime), plus Astro/Tailwind for the marketing site
- **Package manager:** Bun workspaces (`bun.lock`), 8-workspace monorepo (`lib`, `plugins/shipwright`, `metrics`, `agent`, `admin`, `task-store`, `chat`, `mcp-server`) plus non-workspace supporting surfaces (`site/`, `brand/`, `scripts/`, `charts/` Helm chart, `demo/`, `agent-types/`)
- **Primary framework(s):** Hono (all HTTP services: metrics, admin, task-store, chat), Prisma + Postgres (admin, task-store, chat), Zod/`@hono/zod-openapi` for schema validation, Astro (site), Playwright (site + admin + metrics E2E), Bun's built-in test runner throughout
- **Detected source roots:** `lib/`, `metrics/src/`, `agent/src/`, `admin/src/`, `task-store/src/`, `chat/src/`, `mcp-server/src/`, `plugins/shipwright/{commands,agents,skills,scripts,references}/`, `scripts/`, `brand/`, `site/src/`, `agent-types/`

**CLAUDE.md layer-structure declaration:** the root CLAUDE.md's `## Test conventions` section declares five concrete layer names via filename suffix, used verbatim below instead of the rubric's generic unit/integration/smoke/E2E labels (unchanged since the 2026-07-16 inventory):

| Suffix | Layer | Covers |
|---|---|---|
| `*.unit.test.ts` | unit | pure logic, no I/O |
| `*.integration.test.ts` | integration | real dependency behavior via recorded fixtures / injected doubles |
| `*.smoke.test.ts` | smoke | HTTP route contracts — in-process `app.request()` (real `Bun.serve()` boot only when there's no Hono app-factory seam) |
| `*.spec.ts` (in `site/`) / `*.e2e.ts` (in `metrics/e2e/`, `admin/e2e/`) | e2e | real-browser Playwright |
| `*.content.test.ts` | content | markdown/prompt-content assertions (commands, skills, agent prompts, agent-type manifests) — no I/O boundary, not one of the four canonical layers but a first-class fifth layer in this repo |

**CLAUDE.md deploy-model declaration:** root CLAUDE.md declares `## Deploy model` as **`direct`** — "ships via Helm chart + GHCR-pinned image tags, with no staging/production GitHub Environments and no deploy-staging→canary→promote-to-production pipeline." Unchanged since the last inventory. Per Step 5 of the SKILL, canary-eligibility tagging is skipped entirely for this repo (see Notes).

## Per-category detail

### 1. Pure business logic

The largest category by file count. Concentrated in:
- **`lib/`** — shared cross-service pure helpers (`pricing.ts`, `org-repo.ts`, `request-context.ts`, `secret-env-vars.ts`, `claim-ttl.ts`), imported by `agent/`, `admin/`, `metrics/`, `task-store/`. `lib/agent-default-tools.ts` was **deleted this cycle** — its role (default tool set for a new agent) is now resolved from the Agent Type manifest instead of a hardcoded constant; no replacement file needed in `lib/` since the resolution logic lives in `admin/src/agent-type-manifest-loader.ts` (category 2, below).
- **Decision/classification logic** — `agent/src/work-selector.ts` (FIFO candidate picker), `task-store/src/ready.ts` / `blocked-by.ts` / `statuses.ts` (dependency-satisfaction rules), `plugins/shipwright/scripts/classify_test_layer.ts`, `plugins/shipwright/scripts/check-helpers.ts`'s `isCleanApproveBody`.
- **Mutable-box refs** — `agent/src/agent-repos-ref.ts`, `agent/src/loop-jobs-ref.ts`: explicitly designed zero-I/O for unit-testability (per their own header comments) and give downstream cron/dispatch code a live view of async-synced state.
- **Pure wire-object builders** — `admin/src/agent-manifest.ts` (K8s Deployment/Secret shapes), `admin/src/dev-auth-guard.ts`.
- **`admin/src/agent-type-registry.ts` (new this cycle)** — the Agent Type manifest's Zod schema, `.strict()` trust-boundary validation, and JSON-Schema generator. Classified as pure business logic: parsing/validating an in-memory YAML-derived object with no I/O of its own (the file read happens in the loader, category 2). High criticality — a manifest-schema regression silently breaks every agent-type resolution downstream.
- **Crypto helpers treated as pure** — `agent/src/crypto.ts`, `admin/src/crypto.ts`, `admin/src/token-crypto.ts`: deterministic given key/IV inputs, no ambient I/O; canonical layer is unit even though the category-classifier's "no I/O" signal is borderline (uses `node:crypto`, which is in-process, not a process boundary).
- **Parsing/validation utilities** — `scripts/check-coverage.ts` (lcov parsing), `scripts/check-config-docs.ts`, `brand/brand-lint.ts`, `brand/build-brand-css.ts`, `admin/src/attachment-validation.ts`, `agent/src/piper-voice.ts` (voice-name validation with injectable readdir).
- **`task-store/src/claim-ttl-buffer-check.ts`** — an opt-in startup sanity check that is pure given its injected env-value inputs; no network/DB call, so it stays unit despite living next to task-store's mostly-integration service layer.

These are already the repo's dominant unit-test surface (many have `*.unit.test.ts` siblings observed during enumeration, not read).

### 2. Service-boundary code

Every workspace has a Prisma-backed service layer (task-store: `task-service.ts`/`pull-request-service.ts`/`token-service.ts`; chat: `message-service.ts`/`thread-service.ts`/`token-service.ts`; admin: `agent-envs.ts`/`agent-cron-jobs.ts`/`agent-chat-tokens.ts`/`agent-work-queue.ts`/`agents.ts`/etc.) plus internal HTTP clients (`metrics/src/lib/task-store-client.ts`, `agent/src/shipwright-*-client.ts`, `admin/src/*-provisioning-client.ts`). The agent's `check-*.ts` / `loop-orchestrator.ts` family is a distinctive service-boundary cluster: it composes GitHub API reads with task-store writes and is the operational core of the dev-task/review/patch/deploy loop — ranked critical; `agent/src/check-review.ts` gained a bundle-completeness gate this cycle (D2198) without a category/layer change.

**New this cycle:** `admin/src/agent-type-manifest-loader.ts` — the `AgentTypeRegistry` class resolves an agent's `typeName` to its parsed manifest by reading `agent-types/{typeName}/manifest.yaml` from disk. This is a real file-I/O boundary (category 2, not category 1), and it now sits upstream of `admin/src/agent-cron-jobs.ts`'s cron reconciliation (which took an injected `AgentTypeManifestResolver` this cycle, replacing the deleted `admin/src/system-crons.ts` static array) and `scripts/seed-dev-agent.ts`'s plugin/tool seeding. Ranked critical: an unhandled failure here (beyond the documented fallback-to-"coding" contract) would break every new-agent provisioning flow and every cron reconcile.

`scripts/hitl.ts` grew from a thin wrapper into a 739-line worker loop this cycle (workspace provisioning mirroring `agent/src/setup.ts`, task-store+admin boot, ready-task polling, Claude Code dispatch keyed by command) — still dev-only tooling, but now complex enough to warrant its own re-review of criticality/test-layer assumptions (see Ambiguous items).

### 3. HTTP routes / public API

Every service (metrics, admin, task-store, chat, mcp-server) exposes a Hono app factory with a route table documented in its own header comment. `admin/src/server.ts` is a pure composition entrypoint. `agent/src/cron-handler.ts` and `agent/src/slack.ts` are treated as route-equivalent (own a wire contract with an external caller even though they aren't URL-routed HTTP). `admin/src/admin-ui.ts`/`admin-ui-pages.ts` gained the required agent-type picker and `missingRequiredEnv` display this cycle (ATS-4.2, #2203) — no category/layer change, still smoke (server-rendered UI). Canonical layer is smoke throughout, consistent with the CLAUDE.md convention (`*.smoke.test.ts` — in-process `app.request()`).

### 4. Error / failure paths

Thin category here — most error handling is folded into the service/route layer rather than living in dedicated retry/circuit-breaker modules (no queue/retry infrastructure observed). Distinct logic-only error modules: `metrics/src/lib/errors.ts`, `admin/src/errors.ts`, `task-store/src/errors.ts`, `chat/src/errors.ts` (typed HTTP error classes — unit), and `agent/src/cutover-validate.ts` (validation gate — unit). `task-store/src/stale-claim-reaper.ts` and `agent/src/pr-state-reconciler.ts` are boundary-involving error/self-heal paths — integration. `agent/src/cron-failure-reporter.ts` is a boundary-involving error path: it catches a thrown cron-tick error, writes an AgentCronRun row via the admin API, and captures to Sentry.

### 5. External integrations

- `admin/src/kubernetes-client.ts` — in-cluster K8s API (critical; already has a `RecordedKubernetesClient` cassette double per its own header comment).
- `admin/src/google-auth-client.ts` — Google OAuth2 (critical, auth path).
- `agent/src/github-app-auth.ts` — GitHub App installation tokens (critical).
- `agent/src/voice.ts` — Groq Whisper / ElevenLabs (medium). `agent/src/piper-voice.ts` is *not* grouped here — it only validates/resolves baked local `.onnx` file paths (no network call); actual Piper synthesis is a future task per its own header comment, so it stays category 1 (unit) for now.
- `admin/src/slack-provisioning-client.ts` — Slack `apps.manifest.create` (high, one-time provisioning flow).
- `lib/sentry.ts` — Sentry SDK wiring (high, observability-critical but not user-facing).
- Third-party SDKs used directly in entrypoints (`@sentry/bun`, `@octokit/*`, `@slack/bolt`) are not separately inventoried beyond the wrapper modules that own them.

### 6. User journeys

Five journeys identified this cycle (four top-level product journeys plus the dev-only HITL loop, which was promoted to its own row given `scripts/hitl.ts`'s growth this cycle — previously implicitly folded into "internal tooling," not separately tracked):

1. **dev-task → review → patch → deploy pipeline** — the core product loop (`/shipwright:dev-task` → `/shipwright:review`/`/shipwright:patch` → `/shipwright:deploy`), spanning `agent/`, `task-store/`, GitHub. Critical — this is the product.
2. **Agent provisioning (now Agent-Type-aware)** — admin creates an Agent record with a required `typeName` (UI picker is now mandatory, implicit creation removed per #2205), which resolves the manifest via `AgentTypeRegistry` → cascades through `agent-provisioner.ts` → K8s Deployment/Secret → task-store/chat-service token minting → default crons/plugins/tools seeded from the manifest → the agent container boots and reports `/health`. Critical — this is how a customer/operator onboards a new agent, and the manifest-driven redesign this cycle changes what "correct" looks like end-to-end (worth a fresh E2E/integration pass, not just re-running old fixtures).
3. **Slack chat with an agent** — DM/mention → chat-svc queue → `agent/src/chat-poller.ts`'s poll/claim loop → Claude session → Slack reply. High.
4. **Marketing site visitor journey** — landing → docs → self-hosted quickstart, already covered by `site/`'s existing Playwright `*.spec.ts` suite per CLAUDE.md. High (revenue/lead-gen path for an OSS project, not transactional revenue).
5. **Local HITL dev loop** (new row this cycle) — `task hitl` → `scripts/hitl.ts` provisions a workspace, boots task-store + admin, polls for the next ready task, and dispatches Claude Code with the right command. Medium — dev-only, not customer-facing, but no longer trivial enough to ignore as pure tooling glue; flagged in Ambiguous items for a human to confirm whether it belongs in the same roster as journeys 1-4 or a separate "developer experience" bucket.

No journey is browser-driven except #4; #1-#3 are best proven by cross-service integration tests composing recorded fixtures (agent ↔ task-store ↔ GitHub-fixture) rather than a literal Playwright E2E, since there is no UI for the pipeline itself. #5 is local-process-only (no browser, no deployed service) and would be proven by process-level integration tests with injected exec/fs, mirroring `scripts/dev-tmux.unit.test.ts`'s existing pattern for the sibling `dev-tmux.ts`.
