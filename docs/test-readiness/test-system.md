## Framework matrix per layer

The stack-matrix default for "TypeScript (Bun)" is `bun test` for unit/integration,
supertest/Hono-test-client for smoke, Playwright for E2E. The repo already implements
all four choices in production, so no override is needed anywhere — the design below
documents the existing choices as the target, not a hypothetical.

| Layer | Framework | Rationale |
|---|---|---|
| Unit | `bun test` | Matches the stack matrix default for TypeScript (Bun). Already the repo's exclusive unit runner (`*.unit.test.ts`, discovered by the default root scan, no `pathIgnorePatterns` entry needed). ## Canary execution contract

Per Step 4 of `test-design/SKILL.md`, the canary-execution contract
(`${CLAUDE_PLUGIN_ROOT}/skills/canary-execution/SKILL.md`) is included below.

**Applicability finding (carried forward from Phase 1, re-confirmed this pass):** root
`CLAUDE.md` declares `## Deploy model` as **`direct`** — "ships via Helm chart +
GHCR-pinned image tags, with no staging/production GitHub Environments and no
deploy-staging→canary→promote-to-production pipeline." A canary suite validates a
**post-deploy, pre-promotion** environment (`staging`) before promoting to
`production`; this repo has no such intermediate environment for the contract to gate.
**The canary execution contract therefore does not apply to this repo today.** This
section documents the contract as reference material (so a future move to a staged
deploy model has zero rediscovery cost) and records what changes to make it apply — it
does not prescribe building `test:canary` now.

### The contract, verbatim (for reference)

- **Entry point:** a dedicated `test:canary` npm script or a dedicated Playwright
  project (e.g. `playwright.canary.config.ts`) — must never reuse `test:smoke` / the
  local smoke runner. CI wires two distinct jobs, `smoke` (pre-merge, boots local deps)
  and `canary` (post-deploy, sets `TEST_TARGET_URL`) — they must not share a script.
- **Mode selection:** every canary-eligible smoke/E2E test reads `TEST_TARGET_URL` at
  process start. Unset → local mode (boot deps inline, hit `localhost`). Set → canary
  mode (skip local boot, hit `$TEST_TARGET_URL` directly, canary-only auth via
  `TEST_AUTH_TOKEN`). Test code is identical; only the setup-fixture layer branches.
- **Eligibility rules (all must hold):** (1) layer ∈ {smoke, E2E}; (2) criticality ∈
  {critical, high}; (3) read-only OR self-cleaning (try/finally teardown even on
  assertion failure); (4) no destructive side effects, canary auth scoped to reject even
  attempts; (5) tolerates eventual consistency via retry-with-backoff; (6) zero
  DB-dependent local setup — a test that boots a local DB is never canary-eligible.
- **Budget:** per-test 95p <5s smoke / <30s E2E; **suite wall-time hard cap 60s total**.
- **Gating:** failing in local mode blocks the PR (local mode is the primary contract).
  Failing in canary mode blocks promotion staging → production. Canary is a **deploy
  gate, never a merge gate**.
- **Canary safety lint:** before promoting a test file to the canary suite, grep it for
  write patterns (`.create`/`.update`/`.delete`/`.insert`/`.upsert`/`POST`/`PUT`/`PATCH`/`DELETE`)
  and classify every match as setup-only-with-teardown, canary-scoped, or unsafe. Any
  unsafe match disqualifies the file — see `canary-execution/SKILL.md` for the full
  step-by-step lint.

### What would need to change for this contract to apply here

1. Stand up a `staging` deploy target (or equivalent pre-production environment) with a
   stable `TEST_TARGET_URL` and a scoped `TEST_AUTH_TOKEN` issuance path.
2. Add a promotion step between "deploy to staging" and "deploy to production" for the
   canary job to gate.
3. Only then: define the critical-path roster (Phase 1's "Critical-path roster (canary
   suite definition)" section, currently empty by design), reserve the already-defined
   `.canary.test.ts` suffix (see `docs/test-readiness/naming.md` — reserved but unused),
   and wire the `smoke` / `canary` CI jobs per the contract above.
4. Until then: **no `test:canary` script, no `.canary.test.ts` files, and no `canary`
   CI job should be created.** The `.canary.test.ts` suffix stays reserved-but-unused in
   `bunfig.toml`'s `pathIgnorePatterns` (already the case) as a naming placeholder only.

**Net effect on this design:** Step 4's usual output (a populated canary CI job, a
`test:canary` script name, a critical-path roster) is replaced with the applicability
finding above. Every other step (frameworks, local substitutes, test-data strategy, CI
pipeline shape, coverage, speed budgets, shared helpers, repo configuration) proceeds
unchanged — none of them depend on canary applying. Unchanged since the 2026-07-26
design; this cycle's changes (`check-review.ts`'s `reviewedCommitSha` guard,
`pr-state-reconciler.ts`'s RDG-1.1 precondition, the new bash chart-drift cluster, the
new `agent/src/browser.ts`) are all integration-layer/service-boundary or
shell-layer changes with no smoke/E2E surface of their own, so none of them newly
bring anything into canary-eligibility scope.

## Test-data strategy

- **Per-service DBs vs. shared:** per-service, already the case — each Prisma-backed
  service (`admin`, `task-store`, `chat`) reads its own `DATABASE_URL_SHIPWRIGHT_<SERVICE>`
  (root `CLAUDE.md`'s "Database env vars" table); no shared connection string anywhere.
  This matches the modern-microservice-convention default and requires no change.
- **Real DB per test run vs. transaction rollback:** real DB per test run. Each DB
  integration test's `beforeEach` spins up a brand-new `PrismaClient` (its own pooled
  connection, `connection_limit` bounding the pool) and `afterEach` disconnects it —
  already the documented pattern in `ci.yml`'s comments. Transaction-rollback isolation
  was considered and rejected: it requires wrapping the service layer's own transaction
  boundaries in an outer test transaction, which the current service-layer interfaces
  don't expose, and real-DB-per-run at this test volume (3 Prisma-backed services, not
  dozens) doesn't yet justify the added complexity. No change this cycle — no new
  Prisma-backed service landed.
- **Factories vs. fixtures:** both, split by purpose — factories (in-line builder
  functions returning valid entity shapes with overridable fields) for DB integration
  tests needing variability across many test cases; hand-authored fixture JSON (the
  existing `src/fixtures/` convention) for recorded-fixture doubles representing a
  specific external-service response shape (stable golden cases, not meant to vary).
  The `task-store/src/routes/prs.ts` `PullRequest` factory used by
  `pull-request-service.integration.test.ts` (or equivalent) gains one optional
  overridable field, `reviewedCommitSha`, mirroring how the existing `commitSha` field
  is already handled — not a new builder.
- **Seed strategy:** explicit, named seed sets per test file — no reliance on
  migration-time seed data. `scripts/seed-*.ts` (dev-only DB seeders) are for local
  `task stack` development, not test seeding; tests seed their own state directly via
  the service layer in `beforeEach`.
- **API-first seeding:** seed through the public API / service layer wherever it exists
  (e.g. `taskService.create(...)` rather than a raw Prisma `create` call in the test),
  per the SKILL's rule that direct DB writes bypass validations and derived-field logic
  that accumulate over time. Direct DB writes are the explicit fallback only for
  corrupt-state or legacy-data tests that the service layer cannot express (e.g.
  `task-store/src/stale-claim-reaper.ts`'s abandoned-claim scenarios, and any test
  exercising `lib/claim-ttl.ts`'s boundary constants against a claim artificially aged
  past `DEFAULT_CLAIM_TTL_MS`). Testing `check-review.ts`'s `reviewedCommitSha`-keyed
  guard (RCS-1.1/1.2/1.3) requires seeding a `PullRequest` row where `reviewedCommitSha`
  and `commitSha` deliberately diverge (the exact scenario the fix closes — a stale
  staged review whose `commitSha` was bumped by an unrelated `patch()` call) — this is
  only expressible by direct field construction through the existing service-layer
  factory, not the public review-posting flow itself, since the divergence is the
  pre-fix bug's signature, not a normal service-layer transition. New this cycle:
  testing `pull-request-service.ts`'s `patch()`'s `ciFailureSignature` streak-tracking
  (CSD-1.1) needs a seed sequence of 3 consecutive `patch()` calls with a matching
  signature to prove the `hitl`/`blockedReason` auto-set fires at
  `CI_FAILURE_BLOCK_THRESHOLD`, plus one case where the signature changes mid-streak to
  prove the counter resets — same factory-extension pattern as `recordSkip()`'s
  existing auto-block tests, not a new seeding mechanism. Testing the new
  `org`/`repo: string | string[]` filters (ORF-1.x) needs seed sets spanning multiple
  orgs/repos to exercise `buildRepoOrgWhere`'s four branches (repos-only, orgs-only,
  both, neither) — `buildRepoOrgWhere` itself is pure and unit-tested directly with
  no seeding at all; only `task-service.ts`/`pull-request-service.ts`'s `list()`/`distinct()`
  integration tests need the multi-org/-repo seed data.
- **Eventual consistency:** the inventory found no queue/retry infrastructure in this
  repo and no async worker/event-bus component. The three async-shaped paths are
  `agent/src/loop-orchestrator.ts`'s poll loop (task-store claim → dispatch → status
  update), `agent/src/chat-poller.ts`'s poll loop (chat-svc queue → agent poll →
  Claude session → reply), and `scripts/hitl.ts`'s dev-loop poll (poll task-store for
  ready work → dispatch Claude Code) — all three are tested by directly awaiting the
  orchestration function under test with an injected `Clock`, not by polling for
  eventual state. `scripts/hitl.ts`'s auto-clone preflight (`computeMissingClones`) and
  `agent-policy.md` template-seeding step are themselves synchronous, injectable-I/O
  pure planning functions (given a repo list + an injectable existence check) — no
  retry/backoff pattern needed, same as its sibling `computeProvisionPlan`. New this
  cycle's session-id threading (CSI-1.x/2.x) is likewise synchronous — `claude.ts`
  captures `session_id` off the leading stream-JSON line within the same awaited
  `_consumeStream` call, no separate poll needed. No wait/poll-with-backoff pattern is
  needed anywhere in this repo's test suite today.

This is the target CI shape and matches `.github/workflows/ci.yml`'s existing job list
(`changes`, `ci`, `site`, `admin-docker-build`, `agent-docker-build`,
`metrics-docker-build`, `e2e`, `admin-e2e`), plus the new standalone
`check-chart-drift.yml` scheduled workflow — no change to the PR-path job graph itself
since 2026-07-26; the scheduled workflow is additive and off the PR critical path.

- **Layer order:** unit → integration → smoke, all inside the single `ci` job (fail-fast
  is intra-job: `bun test` stops the whole `task test:coverage` run on first failure by
  default within a package, and `task ci`'s step order means lint/typecheck fail before
  the test step ever runs). E2E (`e2e`, `admin-e2e`) runs `needs: ci` — required to
  merge but only after the unit/integration/smoke combined job is green. Content tests
  run alongside unit inside the same `bun test` invocation — no separate CI stage. The
  6 new command-file content tests this cycle slot in the same way with zero pipeline
  change. **Canary does not appear** — see the Canary execution contract section; there
  is no post-deploy stage in a `direct` deploy model for a canary job to occupy.
  **New this cycle:** `agent-docker-build` gains a `verify-browser-launch.ts` step,
  invoked via `docker run` against the just-built image (not `bun test`) — it proves
  Chromium launches under the pod's restricted `securityContext`, a precondition the
  in-process `ci` job cannot verify since it doesn't run inside the built container. The
  new bash chart-drift cluster's test suite (`test-check-chart-drift.sh`) runs as its
  own dedicated `bash` step, outside `task test:coverage` entirely — same pattern as
  the pre-existing `test-auto-bump-chart.sh`, not a new CI stage shape, just one more
  script alongside it. `check-chart-drift.yml` itself is a new **scheduled** workflow
  (periodic drift comparison, not PR-triggered) — it sits outside the PR-path diagram
  above entirely and does not gate merges.
- **Fail-fast:** a unit failure fails the whole `ci` job before `e2e`/`admin-e2e` run
  (`needs: ci`) — same job, same process, same `bun test` invocation.
- **Parallelism (per-workspace matrix — evaluated against Step 6's override
  conditions):** the `ci` job runs unit+integration+smoke as **one combined job across
  all 8 workspaces** (`task test:coverage` → `bun test --coverage` at the repo root),
  not a per-workspace matrix. Checked against the three override conditions:
  - **(a) Budget miss:** no — full-suite wall time (measured baseline: 2m01s job
    wall-clock, 35.82s `Test` step — see Speed budgets below) sits comfortably inside
    the <15min PR budget. This cycle's delta (4 new source files, 1 new bash test file,
    a handful of expanded functions, no deletions) adds a proportionally small number
    of new tests; not close to threatening the budget.
  - **(b) Documented flake/slowness history:** two pre-existing full-suite flakes
    remain on record (`metrics/` — ~15 pre-existing test failures reproducing on clean
    `main`, and `admin/` — a 1-test flake that varies which test) but neither is
    isolated by workspace-matrix sharding today, and sharding would not fix either
    (both are order/environment flakes, not slowness). Not a justification for a
    matrix split.
  - **(c) Overhead-justified parallel savings:** no — at current per-workspace test
    volume, an 8-way matrix's fixed per-job overhead (checkout, `bun install`, Postgres
    container init × 8) still would not pay for itself 2x over versus one combined
    job's single setup cost.

  **Conclusion: keep the single combined `ci` job.** Unchanged from the prior design —
  none of the three override conditions hold, and this cycle's delta doesn't move any
  of them.
- **Budget:** <15min total per PR — see Speed budgets below.

### Naming convention and runner-exclusion config

Both already exist in this repo, confirmed against `docs/test-readiness/naming.md` and

## Coverage targets

Single coverage floor per Step 7 — no per-tier CI thresholds in the enforcement
mechanism itself. This matches the repo's existing gate exactly: `scripts/check-coverage.ts`
already enforces an aggregate 80/80 line/function floor via `task test:coverage`, with
no per-file or per-criticality carve-out. Criticality (critical ~95%, high ~80%, medium
smoke-only) drives **prioritization** during Phase 4/5 task ordering, not a separate CI
gate — writing critical-tier tests first, not a different enforced threshold per tier.

while the tiered targets above (critical ~95%, high ~80%, medium smoke-only) still

design intent, not a second CI gate.

### Branch protection (`main`)

- **Required PR** — no direct pushes (verify in Phase 4 against the live GitHub

- **Required status checks:** `ci` (lint/typecheck/unit/integration/smoke/secret-scan),

  check** — it's a scheduled workflow (periodic drift comparison), not a PR-triggered
  job, so it has no `head_sha` to attach a required-check status to; same reasoning
  category as canary not being a merge gate.
- **Require branches up to date before merging:** **no.**
- **Require conversation resolution before merging:** **no.**
- **Required approving reviews:** **0.**
- **Enforce on admins:** **no.**

`shipwright-deploy` is enabled for this repo, so most PRs are agent-authored and
agent-reviewed, and `deploy.md` Step 4b merges every PR with `gh pr merge --admin` by
design, not as an emergency exception. `--admin` bypasses branch protection wholesale,
so all four settings above are moot for the actual merge path: GitHub blocks
self-APPROVE via the API so a required-review count can never be satisfied by the
pipeline itself, `enforce_admins: true` would either block every automated merge or
require the merging account to be a permanent `bypass_actor`, "up to date" burns real CI
minutes on every merge, and conversation resolution isn't reliably enforced by the
pipeline either. These are the standard values for every shipwright repo, one flat
default rather than a per-repo choice; see `repo-config/SKILL.md`'s Branch protection
section for the full reasoning. Unchanged this cycle.

## Gaps and blockers summary

For Phase 4 (`test-roadmap`) triage — every item below is a **design decision or gap**,
not an existing-test audit finding (that's Phase 3):

1. **`.github/PULL_REQUEST_TEMPLATE.md` already exists — not a gap.** No Phase 4 action
   needed. Carried forward.
2. **Recorded-fixture coverage is partial.** Four `Recorded*`/offline-fixture
   implementations exist; the inventory names roughly a dozen more `Http*Client`/SDK-
   wrapper modules that need the same pattern extended to them (full list in the Local
   execution architecture table above). Carried forward, unchanged in scope this cycle.
3. **Canary execution contract is fully deferred**, contingent on a future staged-deploy
   model — not a gap, a correct non-applicability finding. Carried forward.
4. **Branch-protection required-checks list should be verified against the live GitHub
   API**, not assumed from `ci.yml`'s job list alone. Carried forward.
5. **`agent/src/piper-voice.ts` is a pending reclassification watch item** (unit today,
   category-5/integration once Piper synthesis lands) — carried forward from Phase 1's
   Ambiguous items, still open (no synthesis code landed yet).
6. **`admin/src/server.ts` (composition entrypoint)** needs exactly one thin smoke test
   confirming the three sub-apps mount correctly under one Hono instance. Carried
   forward; Phase 3 should confirm whether this test already landed.
7. **New this cycle — the bash "shell" layer needs a formal documentation decision.**
   `.github/workflows/lib/chart-tag-utils.sh` / `chart-drift-check.sh` and their
   `test-*.sh` siblings are genuinely tested code units that fall entirely outside the
   `bun test` runner and the five-suffix convention. This design treats it as a sixth
   layer (see Framework matrix and Naming convention sections above) but recommends a
   human either (a) formally document it in `CLAUDE.md`'s `## Test conventions` table
   and `docs/test-readiness/naming.md`, or (b) confirm it should stay an unofficial
   exception. Not a coverage gap — `test-check-chart-drift.sh` already exists — a
   documentation-completeness gap.
8. **New this cycle — `agent/src/check-review.ts`'s `reviewedCommitSha`-keyed guard
   (RCS-1.1/1.2/1.3) needs a dedicated integration-test case for the divergent-value
   scenario.** The fix's entire value is in the case where `reviewedCommitSha` and
   `commitSha` differ (a `patch()`-driven `commitSha` bump after a stale staged review)
   — testing only the case where they match doesn't prove the fix. Needs the fixture
   helper described in Shared helpers above.
9. **New this cycle — `agent/src/pr-state-reconciler.ts`'s RDG-1.1 bundle-mate
   precondition on the DIRECT path needs a dedicated integration-test case.** The gap
   this closes (a trailing sibling task on a multi-task branch riding a bundle-mate's
   real merge to "merged" via its own `task.pr` field alone, without its own `startedAt`
   ever being set) was previously observed live across 6 tasks (IC-1.2/1.3/1.4, DPF-2.2,
   PW-1.2, SBA-1.2) before this fix — a regression test reproducing that exact scenario
   (bundle-mate merged, sibling's own `startedAt` unset) is the only way to prove the
   precondition actually gates the direct path now, not just the already-tested
   branch-fallback path.
10. **New this cycle — `agent/src/browser.ts` and `agent/scripts/verify-browser-launch.ts`
    need integration + CI-step coverage respectively, once tests are actually written.**
    See the Local execution architecture and Framework matrix sections above for the
    split: `browser.ts`'s wrapper logic (arg construction, launch-failure handling) is
    `bun test` integration-testable against a real Chromium launch;
    `verify-browser-launch.ts`'s environment-capability claim (Chromium launches under
    the *built image's* restricted `securityContext`) can only be proven by the
    `agent-docker-build` CI step actually running it — no `bun test` file can substitute.
11. **Journey #5 (local HITL dev-loop bootstrap) has no existing coverage shape to
    reconcile against**, since `scripts/hitl.ts` crossed the journey threshold in the
    2026-07-30 cycle (auto-clone preflight + policy-seeding added). Phase 3 should
    treat this as a genuinely new item, not a re-classification of existing coverage —
    flag for Phase 4 to scope as integration-composed tests per the Test-data strategy
    section above (`computeMissingClones` unit-testable directly; the full
    clone→seed→boot→poll sequence needs an integration harness with an injected `gh`
    exec fake). Carried forward unchanged this cycle — no further `hitl.ts` scope
    growth since 2026-07-31.
12. **New this cycle — `task-store/src/pull-request-service.ts`'s `ciFailureSignature`
    streak-to-auto-block path (CSD-1.1) needs a dedicated integration-test sequence.**
    The fix's value is entirely in the streak behavior (3 consecutive matching
    signatures → auto `hitl`+`blockedReason`; a differing signature mid-streak →
    reset to 1) — a single-call test proves nothing about the threshold logic. Needs
    the fixture helper described in Shared helpers above. Mirrors gap #9's shape
    (a multi-call state-machine precondition, not a single-assertion boundary check).
13. **New this cycle — the ORF-1.x/2.x multi-repo/org filter extension needs
    integration coverage spanning `buildRepoOrgWhere`'s branch matrix at the
    service-layer boundary**, on top of `repo-org-filter.unit.test.ts`'s existing
    direct unit coverage of the pure builder itself. The unit test proves the builder
    is correct in isolation; the integration test is needed to prove `list()`/
    `distinct()` actually thread the resulting Prisma where-fragment through to a real
    query correctly (e.g. the `AND`-of-`repo-in`-and-`org-OR` combined-filter case).
14. **New this cycle — `agent/src/check-review.ts`'s requested-reviewer inclusion
    (RRR-1.1) needs a dedicated integration-test case** proving a self-authored PR
    *is* included when the agent is a requested reviewer, layered on top of an
    existing case proving the author-allowlist exclusion still applies unconditionally
    even when `reviewRequests` is set (since any author with write access, including
    the PR's own author, can set requested reviewers — it isn't itself an
    access-control signal). Two cases needed, not one, to prove both halves of the
    fix hold simultaneously.
