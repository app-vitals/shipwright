  this commit). Shapes the canary contract section and the repo-configuration section

- **Repo's own layer convention (used verbatim, per CLAUDE.md fallback):** this repo
  already declares five concrete layer names by filename suffix — `*.unit.test.ts`,
  `*.integration.test.ts`, `*.smoke.test.ts`, `*.spec.ts` (site) / `*.e2e.ts` (metrics,
  admin), and `*.content.test.ts` — mapping cleanly onto the rubric's
  unit/integration/smoke/e2e plus a repo-specific fifth "content" layer for
  markdown/prompt assertions. This design reuses those names rather than introducing
  the rubric's generic labels. The inventory also carries forward a repo-specific,
  unofficial **sixth "shell" layer** — `.github/workflows/test-*.sh`, plain-bash
  assertion scripts run via `bash <file>.sh` rather than `bun test`, covering CI

  wiring, even though the *design intent* (pure logic, no I/O) is unit-equivalent.

## Framework matrix per layer

The stack-matrix default for "TypeScript (Bun)" is `bun test` for unit/integration,
supertest/Hono-test-client for smoke, Playwright for E2E. The repo already implements
all four choices in production, so no override is needed anywhere — the design below
documents the existing choices as the target, not a hypothetical.

| Layer | Framework | Rationale |
|---|---|---|
| Unit | `bun test` | Matches the stack matrix default for TypeScript (Bun). Already the repo's exclusive unit runner (`*.unit.test.ts`, discovered by the default root scan, no `pathIgnorePatterns` entry needed). No I/O, no framework boot — Bun's runner is fast enough that no alternative is justified. ## Canary execution contract

Per Step 4 of `test-design/SKILL.md`, the canary-execution contract
(`${CLAUDE_PLUGIN_ROOT}/skills/canary-execution/SKILL.md`) is included below.

**Applicability finding (carried forward from Phase 1, re-confirmed this pass):** root
`CLAUDE.md` declares `## Deploy model` as **`direct`** — "ships via Helm chart +
GHCR-pinned image tags, with no staging/production GitHub Environments and no
deploy-staging→canary→promote-to-production pipeline." A canary suite validates a
**post-deploy, pre-promotion** environment (`staging`) before promoting to
`production`; this repo has no such intermediate environment for the contract to gate.
**The canary execution contract therefore does not apply to this repo today.** This
section documents the contract as reference material (so a future move to a staged
deploy model has zero rediscovery cost) and records what changes to make it apply — it
does not prescribe building `test:canary` now.

### The contract, verbatim (for reference)

- **Entry point:** a dedicated `test:canary` npm script or a dedicated Playwright
  project (e.g. `playwright.canary.config.ts`) — must never reuse `test:smoke` / the
  local smoke runner. CI wires two distinct jobs, `smoke` (pre-merge, boots local deps)
  and `canary` (post-deploy, sets `TEST_TARGET_URL`) — they must not share a script.
- **Mode selection:** every canary-eligible smoke/E2E test reads `TEST_TARGET_URL` at
  process start. Unset → local mode (boot deps inline, hit `localhost`). Set → canary
  mode (skip local boot, hit `$TEST_TARGET_URL` directly, canary-only auth via
  `TEST_AUTH_TOKEN`). Test code is identical; only the setup-fixture layer branches.
- **Eligibility rules (all must hold):** (1) layer ∈ {smoke, E2E}; (2) criticality ∈
  {critical, high}; (3) read-only OR self-cleaning (try/finally teardown even on
  assertion failure); (4) no destructive side effects, canary auth scoped to reject even
  attempts; (5) tolerates eventual consistency via retry-with-backoff; (6) zero
  DB-dependent local setup — a test that boots a local DB is never canary-eligible.
- **Budget:** per-test 95p <5s smoke / <30s E2E; **suite wall-time hard cap 60s total**.
- **Gating:** failing in local mode blocks the PR (local mode is the primary contract).
  Failing in canary mode blocks promotion staging → production. Canary is a **deploy
  gate, never a merge gate**.
- **Canary safety lint:** before promoting a test file to the canary suite, grep it for
  write patterns (`.create`/`.update`/`.delete`/`.insert`/`.upsert`/`POST`/`PUT`/`PATCH`/`DELETE`)
  and classify every match as setup-only-with-teardown, canary-scoped, or unsafe. Any
  unsafe match disqualifies the file — see `canary-execution/SKILL.md` for the full
  step-by-step lint.

### What would need to change for this contract to apply here

1. Stand up a `staging` deploy target (or equivalent pre-production environment) with a
   stable `TEST_TARGET_URL` and a scoped `TEST_AUTH_TOKEN` issuance path.
2. Add a promotion step between "deploy to staging" and "deploy to production" for the
   canary job to gate.
3. Only then: define the critical-path roster (Phase 1's "Critical-path roster (canary
   suite definition)" section, currently empty by design), reserve the already-defined
   `.canary.test.ts` suffix (see `docs/test-readiness/naming.md` — reserved but unused),
   and wire the `smoke` / `canary` CI jobs per the contract above.
4. Until then: **no `test:canary` script, no `.canary.test.ts` files, and no `canary`
   CI job should be created.** The `.canary.test.ts` suffix stays reserved-but-unused in
   `bunfig.toml`'s `pathIgnorePatterns` (already the case) as a naming placeholder only.

**Net effect on this design:** Step 4's usual output (a populated canary CI job, a
`test:canary` script name, a critical-path roster) is replaced with the applicability
finding above. Every other step (frameworks, local substitutes, test-data strategy, CI
pipeline shape, coverage, speed budgets, shared helpers, repo configuration) proceeds
unchanged — none of them depend on canary applying. Unchanged since the 2026-07-26
design; this cycle's changes (the `lib/http.ts` dedup, `compute-review-verdict.ts`,
`check-patch.ts`'s DRO-1.2, the two `claim()` race-closes, and
`pr-state-reconciler.ts`'s scope reduction) are all unit/integration-layer or
service-boundary changes with no smoke/E2E surface of their own, so none of them newly
bring anything into canary-eligibility scope.

## Test-data strategy

- **Per-service DBs vs. shared:** per-service, already the case — each Prisma-backed
  service (`admin`, `task-store`, `chat`) reads its own `DATABASE_URL_SHIPWRIGHT_<SERVICE>`
  (root `CLAUDE.md`'s "Database env vars" table); no shared connection string anywhere.
  This matches the modern-microservice-convention default and requires no change.
- **Real DB per test run vs. transaction rollback:** real DB per test run. Each DB
  integration test's `beforeEach` spins up a brand-new `PrismaClient` (its own pooled
  connection, `connection_limit` bounding the pool) and `afterEach` disconnects it —
  already the documented pattern in `ci.yml`'s comments. Transaction-rollback isolation
  was considered and rejected: it requires wrapping the service layer's own transaction
  boundaries in an outer test transaction, which the current service-layer interfaces
  don't expose, and real-DB-per-run at this test volume (3 Prisma-backed services, not
  dozens) doesn't yet justify the added complexity. No change this cycle.
- **Factories vs. fixtures:** both, split by purpose — factories (in-line builder
  functions returning valid entity shapes with overridable fields) for DB integration
  tests needing variability across many test cases; hand-authored fixture JSON (the
  existing `src/fixtures/` convention) for recorded-fixture doubles representing a
  specific external-service response shape (stable golden cases, not meant to vary).
  New this cycle: the `PullRequest` factory used by `pull-request-service`'s
  integration suite needs no new field — the CRF-1.1 race-close test exercises the
  same shape with two concurrent callers, not a new field.
- **Seed strategy:** explicit, named seed sets per test file — no reliance on
  migration-time seed data. `scripts/seed-*.ts` (dev-only DB seeders) are for local
  `task stack` development, not test seeding; tests seed their own state directly via
  the service layer in `beforeEach`.
- **API-first seeding:** seed through the public API / service layer wherever it exists
  (e.g. `taskService.create(...)` rather than a raw Prisma `create` call in the test),
  per the SKILL's rule that direct DB writes bypass validations and derived-field logic
  that accumulate over time. Direct DB writes are the explicit fallback only for
  corrupt-state or legacy-data tests that the service layer cannot express (e.g.
  `task-store/src/stale-claim-reaper.ts`'s abandoned-claim scenarios, and any test
  exercising `lib/claim-ttl.ts`'s boundary constants against a claim artificially aged
  past `DEFAULT_CLAIM_TTL_MS`). New this cycle: testing the CRF-1.1 claim-race close
  requires two concurrent callers racing `claim()` on the same seeded row — seeded via
  the normal service-layer `create()` call, then raced via two parallel `claim()`
  invocations issued without awaiting between them, asserting exactly one resolves and
  the other throws `ConflictError`. This is expressible entirely through the public
  service-layer API — no direct DB write needed, unlike the `reviewedCommitSha`
  divergence case below. Testing `check-review.ts`'s `reviewedCommitSha`-keyed guard
  (RCS-1.1/1.2/1.3, carried forward) still requires seeding a `PullRequest` row where
  `reviewedCommitSha` and `commitSha` deliberately diverge — only expressible by direct
  field construction through the existing service-layer factory, since the divergence
  is the pre-fix bug's signature, not a normal service-layer transition.
- **Eventual consistency:** the inventory found no queue/retry infrastructure in this
  repo and no async worker/event-bus component. The three async-shaped paths are
  `agent/src/loop-orchestrator.ts`'s poll loop (task-store claim → dispatch → status
  update), `agent/src/chat-poller.ts`'s poll loop (chat-svc queue → agent poll →
  Claude session → reply), and `scripts/hitl.ts`'s dev-loop poll (poll task-store for
  ready work → dispatch Claude Code) — all three are tested by directly awaiting the
  orchestration function under test with an injected `Clock`, not by polling for
  eventual state. No wait/poll-with-backoff pattern is needed anywhere in this repo's
  test suite today. This cycle's two `claim()` race-closes are tested with concurrent
  *synchronous* calls (both issued in the same test tick, raced via `Promise.all`), not
  an eventual-consistency pattern — the race is a within-process concurrency property,
  not a cross-process eventual-consistency one.

  conditions):** the `ci` job runs unit+integration+smoke as **one combined job across

  - **(a) Budget miss:** no — full-suite wall time (measured baseline: 2m01s job
    wall-clock, 35.82s `Test` step — see Speed budgets below) sits comfortably inside
    the <15min PR budget. This cycle's delta (3 new source files, no new bash test
    file, several incremental guard-condition test cases, no deletions of test
    surface) adds a proportionally small number of new tests; not close to threatening
    the budget.
  - **(b) Documented flake/slowness history:** two pre-existing full-suite flakes
    remain on record (`metrics/` — ~15 pre-existing test failures reproducing on clean
    `main`, and `admin/` — a 1-test flake that varies which test) but neither is
    isolated by workspace-matrix sharding today, and sharding would not fix either
    (both are order/environment flakes, not slowness). Not a justification for a
    matrix split.
  - **(c) Overhead-justified parallel savings:** no — at current per-workspace test
    volume, an 8-way matrix's fixed per-job overhead (checkout, `bun install`, Postgres
    container init × 8) still would not pay for itself 2x over versus one combined
    job's single setup cost.

  **Conclusion: keep the single combined `ci` job.** Unchanged from the prior design —
  none of the three override conditions hold, and this cycle's delta doesn't move any
  of them.
- **Budget:** <15min total per PR — see Speed budgets below.
- **Coverage toolchain:** `lcov` (Bun's native coverage reporter) — `bun test --coverage

  preserving compatibility for repos without a recorded toolchain. For shipwright itself,
  the toolchain is Bun/lcov (no explicit `**Coverage toolchain:**` field needed, lcov is

| Smoke | <5 s | <15 s | <30 s sequential / <60 s full |
| E2E | <30 s | <90 s | <10 min |
| Full PR pipeline | — | — | **<15 min** |
| Canary suite | — | — | **<60 s** (not applicable — see Canary execution contract) |

**Parallelization plan:**

- **Unit + integration + smoke (the combined `ci` job):** Bun's test runner
  parallelizes within a single process by default; no explicit worker-count flag is set
  in `task test` / `task test:coverage`, and none is newly prescribed — the single-job
  shape means the whole layer stack runs as one `bun test` invocation with Bun's own
  internal concurrency. Sufficient at current suite size to hit the <15min full-PR
  budget with headroom. The two new `claim()` concurrent-race regression tests
  deliberately race *within* a single test case (two `Promise.all`-raced calls), not
  across parallel test-runner workers — that's a correctness property of the test
  itself, not a parallelism concern.
- **E2E (`e2e`, `admin-e2e`):** two separate CI jobs, run in parallel with each other
  (both `needs: ci`, no dependency between them) — justified because they exercise
  genuinely different Playwright projects/servers, not a cost-only split of one logical
  suite. Within each job, Playwright's own default worker parallelism applies (no
  custom `workers:` override in any of the three `playwright.config.ts` files).
- **If suite growth later threatens the <15min budget:** re-evaluate the per-workspace
  matrix override conditions in the CI pipeline shape section above — condition (a)
  (budget miss) is the trigger to revisit, not a fixed test-count threshold. This
  cycle's ~3-file net delta is not, on its own, that trigger.

**Measured baseline (aggregate-first, per the two-tier model in `speed-budgets/SKILL.md`):**
the primary, continuously-tracked number is the Tier 1 aggregate in
[`speed-baseline.md`](./speed-baseline.md#aggregate-tier-1) — pulled fresh from the most
recent green `lint / typecheck / test` CI run: [run 30415213982](https://github.com/app-vitals/shipwright/actions/runs/30415213982)
(2026-07-29, commit `1a6a085d`), job wall-clock 2m01s against the <15 min Full-PR-pipeline
budget (13% of budget, well within — no escalation triggered). `speed-baseline.md`'s
Section 3 table is the Tier-2 per-package/per-layer breakdown (unit 1.05s–2.50s per
package, integration 0.15s–5.35s per package, smoke 3.24s–4.62s per package, E2E 4s–40s
via CI, across plugin/metrics/agent/admin/site) — last produced 2026-07-15, supplementary
and on-demand: it refreshes only when the Tier 1 aggregate trips the escalation formula,
not on a fixed cadence. This cycle's delta (a handful of new/incremental test cases,
well under the volume that would move the aggregate meaningfully) does not trip the
escalation formula — no refresh triggered. See `speed-baseline.md` for the full
breakdown and methodology.

### Branch protection (`main`)

- **Required PR** — no direct pushes (verify in Phase 4 against the live GitHub
  branch-protection API, not assumed from this doc).
- **Required status checks:** `ci` (lint/typecheck/unit/integration/smoke/secret-scan),
  `site` (build/brand-lint/Playwright), `admin-docker-build` (includes the
  `verify-browser-launch.ts` step), `agent-docker-build`, `metrics-docker-build`, `e2e`,
  `admin-e2e` — every job in `.github/workflows/ci.yml` that isn't itself gated to skip
  on version-bump-only changes. **`check-chart-drift.yml` is NOT a required status
  check** — it's a scheduled workflow (periodic drift comparison), not a PR-triggered
  job, so it has no `head_sha` to attach a required-check status to; same reasoning
  category as canary not being a merge gate.
- **Require branches up to date before merging:** **no.**
- **Require conversation resolution before merging:** **no.**
- **Required approving reviews:** **0.**
- **Enforce on admins:** **no.**

`shipwright-deploy` is enabled for this repo, so most PRs are agent-authored and
agent-reviewed, and `deploy.md` Step 4b merges every PR with `gh pr merge --admin` by
design, not as an emergency exception. `--admin` bypasses branch protection wholesale,
so all four settings above are moot for the actual merge path: GitHub blocks
self-APPROVE via the API so a required-review count can never be satisfied by the
pipeline itself, `enforce_admins: true` would either block every automated merge or
require the merging account to be a permanent `bypass_actor`, "up to date" burns real CI
minutes on every merge, and conversation resolution isn't reliably enforced by the
pipeline either. These are the standard values for every shipwright repo, one flat
default rather than a per-repo choice; see `repo-config/SKILL.md`'s Branch protection
section for the full reasoning. Unchanged this cycle.
- **Canary status check:** not applicable / not included — see Canary execution
  contract section.

not an existing-test audit finding (that's Phase 3):

3. **Canary execution contract is fully deferred**, contingent on a future staged-deploy
   model — not a gap, a correct non-applicability finding. Carried forward.

   Ambiguous items, still open (no synthesis code landed yet).
6. **`admin/src/server.ts` (composition entrypoint)** needs exactly one thin smoke test
   confirming the three sub-apps mount correctly under one Hono instance. Carried
   forward; Phase 3 should confirm whether this test already landed.
7. **The bash "shell" layer still needs a formal documentation decision.**
   `.github/workflows/lib/chart-tag-utils.sh` / `chart-drift-check.sh` and their
   `test-*.sh` siblings are genuinely tested code units that fall entirely outside the

8. **`agent/src/check-review.ts`'s `reviewedCommitSha`-keyed guard (RCS-1.1/1.2/1.3)

   gates the direct path now. Carried forward.

    integration + CI-step coverage respectively, once tests are actually written.**
    See the Local execution architecture and Framework matrix sections above for the
    split: `browser.ts`'s wrapper logic is `bun test` integration-testable against a
    real Chromium launch; `verify-browser-launch.ts`'s environment-capability claim can

    forward.

    (`computeMissingClones` unit-testable directly; the full clone→seed→boot→poll
    sequence needs an integration harness with an injected `gh` exec fake). Carried
    forward, unchanged this cycle.
12. **`task-store/src/pull-request-service.ts`'s `ciFailureSignature` streak-to-auto-block

13. **The ORF-1.x/2.x multi-repo/org filter extension needs integration coverage
