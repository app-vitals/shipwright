# Test System Design

> Phase 2 of the test-readiness pipeline. The greenfield blueprint for the ideal test system
> that would satisfy the Phase 1 inventory. Does **not** account for existing tests, and does
> not verify existing coverage — every recommendation below is a *target state*, not a
> confirmed fact about what currently exists in `admin/`, `agent/`, `task-store/`, etc. Phase 3
> (`test-migration`) reconciles this blueprint against the tests that actually exist today, and
> is the point at which any implied "does X already exist" claim below must be verified against
> the working tree before being trusted for effort estimation or task scoping.
>
> Generated by `/test-design` on 2026-09-23 against `app-vitals/shipwright`
> (worktree: `docs/test-readiness-refresh-20260923`), from

## Stack profile (from inventory)

- **Language(s):** TypeScript (Bun runtime), plus Astro/Tailwind for the marketing site; a
  small real bash cluster for CI chart-tag logic (`.github/workflows/lib/*.sh`).
- **Package manager:** Bun workspaces (`bun.lock`), 8-workspace monorepo (`lib`,
  `plugins/shipwright`, `metrics`, `agent`, `admin`, `task-store`, `chat`, `mcp-server`) plus
  non-workspace supporting surfaces (`site/`, `brand/`, `scripts/`, `charts/` Helm chart,
  `demo/`, `.github/workflows/`).
- **Primary frameworks:** Hono (all HTTP services), Prisma + Postgres (admin, task-store,
  chat — one DB per service, never a shared connection), Zod / `@hono/zod-openapi` for schema
  validation, Astro (site), Playwright (`site/*.spec.ts`, `admin/e2e/*.e2e.ts`,
  `metrics/e2e/*.e2e.ts`), Bun's built-in test runner throughout.
- **Existing layer convention (from CLAUDE.md `## Test conventions`):** this repo already
  declares five concrete layer names by filename suffix — `*.unit.test.ts`,
  `*.integration.test.ts`, `*.smoke.test.ts`, `*.spec.ts`/`*.e2e.ts` (e2e), and
  `*.content.test.ts` (a repo-specific fifth layer for markdown/prompt-content assertions, no
  I/O boundary). The inventory additionally flags an unofficial sixth "shell" layer
  (`.github/workflows/test-*.sh`, run via `bash`, no `bun test` suffix) and an unresolved
  seventh "compile-time parity check" pattern (`*.check.ts`, type-checked only, never executed
  by `bun test`). This blueprint adopts the five declared suffixes and the unofficial shell
  layer as-is — see "Framework matrix" and "Naming convention" below for why no override is
  warranted here.
- **Deploy model (declared in CLAUDE.md):** `direct` — ships via Helm chart + GHCR-pinned image
  tags, **no staging/production GitHub Environments, no deploy→canary→promote pipeline**. This
  has a direct, load-bearing effect on the Canary execution contract section below.
- **Coverage toolchain (from CLAUDE.md `task test:coverage`):** `lcov` — Bun's native
  `bun test --coverage --coverage-reporter=lcov`, parsed and gated by `scripts/check-coverage.ts`
  (`LcovParser`).

## Framework matrix per layer

| Layer | Framework | Rationale |
|---|---|---|
| Unit | `bun test` (`*.unit.test.ts`) | Stack-profile default for TypeScript/Bun. Zero extra runtime dependency, fastest possible cold-start for a suite that must stay <30s. |
| Integration | `bun test` + testcontainers (Postgres) / recorded-fixture doubles for every non-DB boundary | Stack-profile default. ## Canary execution contract

**Not applicable — `deploy_model: direct`.**

This repo's root `CLAUDE.md` declares `## Deploy model` as `direct`: ships via Helm chart +
GHCR-pinned image tags, with **no staging/production GitHub Environments** and no
deploy→canary→promote-to-production pipeline. The pipeline-wide convention across all four
phases (`test-inventory` Step 5, this skill, `test-roadmap` Milestone 3) is to skip canary
plumbing entirely when `deploy_model != 'staged'` rather than design a contract with nothing to
run it against — the Phase 1 inventory already reflects this ("Not applicable... no items are
tagged `canary-eligible: true`").

Concretely, this blueprint prescribes **none** of the following for this repo:
- no `test:canary` npm script / `playwright.canary.config.ts` entry point
- no `TEST_TARGET_URL` env-var mode switch
- no `canary` CI job
- no `TEST_CANARY_API_KEY` secret (see Repo configuration below)

The repo's `bunfig.toml` already reserves the `*.canary.test.ts` suffix in
`pathIgnorePatterns` proactively, "for the future canary suite defined by the canary-execution
skill contract" — a forward-compatibility placeholder, not a live contract. That reservation is
correct and should stay as-is; this blueprint does not ask for it to be filled in.

**If a future revision of this repo adopts a staged deploy model** (a real `staging`
environment sitting between merge and production), re-run `/test-design`. This section would
then populate with the full contract from
`${CLAUDE_PLUGIN_ROOT}/skills/canary-execution/SKILL.md`: a dedicated `test:canary` entry point
never reusing `test:smoke`, the `TEST_TARGET_URL` mode switch, the six eligibility rules
(smoke/E2E only, critical/high tier only, read-only-or-self-cleaning, no destructive side
effects, eventual-consistency tolerance, zero DB-dependent local-mode tests), and the <60s
suite-wall-time deploy-gate budget.

## Test-data strategy

- **Per-service DBs vs. shared:** per-service, already this repo's declared convention — admin,
  task-store, and chat each own a `DATABASE_URL_SHIPWRIGHT_<SERVICE>`, never a shared
  connection (per CLAUDE.md's "Database env vars" table). This blueprint keeps that shape for
  the test DBs too — three isolated test databases, not one shared schema.
- **Real DB per test run vs. transaction rollback:** real DB per test **run** (session-scoped
  container, migrated once), with **truncate-between-tests** for isolation rather than
  per-test transaction-rollback wrapping. Reason: several service-layer methods already open
  their own interactive Prisma `$transaction` internally (e.g. task-store's claim/release/
  complete paths, session-service's task-bulk-create path) — wrapping the *test* itself in an
  outer transaction would either nest transactions unnaturally or mask transaction-boundary
  bugs the integration layer exists to catch. Truncate-all-tables in a shared `beforeEach` is
  simpler and doesn't fight the app code's own transaction usage.
- **Factories vs. fixtures:** factories (e.g. `createTestTask()`, `createTestAgent()`,
  `createTestPullRequest()`) for anything that needs variability across test cases; fixtures
  (recorded GitHub/Slack/K8s/Google/Okta/Groq/ElevenLabs JSON payloads) for stable golden cases
  where the shape of a third-party response is the thing under test, not the local state.
- **Seed strategy:** explicit, named seed sets per feature area — e.g. `seedMinimalOrg()`,
  `seedAgentWithCrons()`, `seedReadyTaskQueue()` — never "whatever the Prisma migration happens
  to leave behind." Each seed function lives next to the service it seeds and is reused across
  that service's integration + smoke tests.
- **API-first seeding:** seed through each service's own service-layer / route handlers (e.g.
  `taskService.createTask()`, not a raw `prisma.task.create()`) wherever the API surface can
  express the desired state, so seeded state exercises the same validations, derived fields,
  and side effects (e.g. `TaskEvent` audit rows, `webhook-dispatcher.ts`'s `task.write` events)
  that production traffic does. Direct Prisma writes are the explicit fallback only for
  state the API can't express — e.g. corrupt/legacy-shaped rows for `stale-claim-reaper.ts` or
  `pr-state-reconciler.ts`'s self-heal-path tests.
- **Eventual consistency:** this repo has several async/background paths that seeded state may
  need to wait on — `task-store/src/webhook-dispatcher.ts` (outbound `task.write` events),
  `chat/src/reply-notifier.ts` (outbound webhook on agent reply), `task-store/src/
  stale-claim-reaper.ts` and `chat/src/stall-reaper.ts` (periodic sweeps), `admin/src/
  session-alert-sweeper.ts` (push-notification sweep), and the `shipwright-loop` cron dispatch
  cycle itself. Any test asserting on state produced by one of these must use a
  retry-with-backoff pattern on the assertion (5 retries, 500 ms base, 5 s hard cap) rather than
  a single synchronous check.

## CI pipeline shape

```
PR opened / synchronized
  │
  ├─▶ changes (path filter: real app code vs. automated version-bump-only diff)
  │        │
  │        ▼ (app == true)
  ├─▶ ci  [single job — boots the shared Postgres 18 service container once]
  │     steps (sequential; a step failure stops the job — this is the fail-fast
  │            mechanism, without paying per-layer job setup/checkout overhead 3x):
  │       1. lint (Biome)
  │       2. check-strings (banned/confidential-string scan)
  │       3. typecheck
  │       4. check-config-docs
  │       5. unit + content   — bun test '**/*.unit.test.ts' '**/*.content.test.ts'
  │       6. integration      — bun test '**/*.integration.test.ts'  (real Postgres)
  │       7. smoke            — bun test '**/*.smoke.test.ts'
  │       8. coverage gate    — scripts/check-coverage.ts against the merged lcov report
  │       9. secret scan (gitleaks)
  │
  ├─▶ shell   — bash .github/workflows/test-check-chart-drift.sh
  │            bash .github/workflows/test-auto-bump-chart.sh
  │
  ├─▶ site        — Astro build → brand-lint → Playwright (*.spec.ts), path-filtered to site/**
  │
  ├─▶ e2e (needs: ci)         — Playwright, metrics dashboard journey
  │
  └─▶ admin-e2e (needs: ci)   — Playwright, admin UI journey (*.e2e.ts)

main branch merge
  │
  └─▶ Helm chart + GHCR image publish only.
      deploy_model: direct — no post-merge canary/promote gate exists to run.
```

- **Layer order:** unit+content → integration → smoke, enforced as ordered steps within one
  job (see diagram) rather than as three separate GitHub Actions jobs. Splitting them into
  three jobs would triple the fixed per-job overhead (checkout, `bun install`, Postgres
  container boot + migrate) for a monorepo whose actual test volume doesn't justify it — the
  same overhead-consciousness the per-workspace matrix-sharding rule (below) applies, applied
  here to layer-splitting instead of workspace-splitting. E2E runs after `ci` passes
  (`needs: ci`), consistent with "lower layers gate higher layers."
- **Fail-fast:** a failing step stops the job — unit+content failing means integration and
  smoke never run in that job execution. E2E jobs additionally gate on the whole `ci` job via
  `needs: ci`.
- **Parallelism:**
  - unit+content: no explicit sharding needed — Bun's single-process test runner is fast
    enough that hundreds of files stay well under the 30s suite target without extra
    configuration. Shard by workspace only if condition (a)/(b)/(c) below trips.
  - integration: single Postgres container per job run, truncate-between-tests isolation (see
    Test-data strategy). No multi-process fan-out against the same DB by default — add it only
    if the suite approaches its 3 min budget.
  - smoke: in-process `app.request()`, no shared external resource — safe to parallelize
    freely if the suite ever needs it, but the <60s target should be reachable single-threaded
    given the surface size.
  - E2E: Playwright's built-in worker sharding. Suggested starting point: `workers: 4` for
    `site/` (many marketing pages), `workers: 2` for `admin/e2e/` and `metrics/e2e/` (fewer,
    heavier specs per the inventory's single-journey description).
- **Budget:** <15 min total per PR (all jobs above, in parallel where the diagram shows
  parallel branches).
- **Coverage toolchain:** `lcov` — Bun's native `bun test --coverage --coverage-reporter=lcov`,
  parsed by `scripts/check-coverage.ts`'s `LcovParser` and gated in the `ci` job's step 8.

### Per-workspace matrix sharding — explicit override, not the default

Default CI shape for this repo is **one job per layer-group** (the combined `ci` job above),
not a per-workspace matrix (`admin-unit`, `agent-unit`, `task-store-unit`, ...). None of the
three override conditions can be evaluated at design time without real suite-timing data, which
is Phase 3's job, not this blueprint's:

1. **(a) Budget miss** — unknown until Phase 3 measures actual wall-time against the <30s/
   <3min/<60s targets.
2. **(b) Documented flake/slowness history** — none exists yet by definition (greenfield
   design); Phase 3 or ongoing CI history would surface this.
3. **(c) Overhead-justified >2x savings** — cannot be computed without (a)'s timing data.

The most plausible future candidates for condition (a), based on inventory size alone (largest
Prisma-backed service-boundary clusters), are the `admin/` and `agent/` integration suites —
flag them for Phase 3/4 to re-evaluate if the combined `ci` job's integration step approaches
its 3-minute budget. Default to the cheaper, single-job shape until real data says otherwise.

### Naming convention and runner-exclusion config

**File-naming convention** (already declared in this repo's CLAUDE.md — adopted as-is per the
Step 2 override rule: no reason exists to invent a different one):

| Suffix | Layer |
|---|---|
| `*.unit.test.ts` | unit |
| `*.integration.test.ts` | integration |
| `*.smoke.test.ts` | smoke |
| `*.spec.ts` (in `site/`) / `*.e2e.ts` (in `admin/e2e/` and `metrics/e2e/`) | e2e |
| `*.content.test.ts` | content |
| `*.canary.test.ts` | reserved, unused while `deploy_model: direct` |

**Runner-exclusion config:**

- **Bun (`bunfig.toml`)** — already excludes `site/**` (Astro's own Playwright suite),
  `metrics/e2e/**` and `admin/e2e/**` (Playwright `*.e2e.ts`), and `*.canary.test.ts` (reserved)
  from the default `bun test` walk via `[test] pathIgnorePatterns`. No change needed.
- **Layer-scoped invocation** — since Bun's `bun test` has no real `--filter`/`--dry-run` flag
  (confirmed against current Bun CLI behavior — any such flag is silently ignored, not
  enforced), layer selection is done via **positional glob arguments**, e.g.
  `bun test '**/*.unit.test.ts' '**/*.content.test.ts'`. This is what the CI steps above use.
- **Playwright `testMatch`** — `site/playwright.config.ts` scoped to `*.spec.ts`;
  `admin/playwright.config.ts` and `metrics/playwright.config.ts` (or equivalent) each scoped
  to `*.e2e.ts` under their own `e2e/` directory (`admin/e2e/`, `metrics/e2e/`).
- **Coverage config `exclude`** — exclude generated code (`lib/admin-types.ts`,
  `lib/task-store-types.ts`, `mcp-server/src/generated-tools.ts`), test infra
  (`metrics/src/lib/test-helpers.ts`, `chat/src/test-fakes.ts`, `scripts/test-env-preload.ts`),
  and fixture directories (`agent/src/fixtures/**`, `**/*.fixtures.ts`) from the lcov report —
  these inflate or deflate the floor without reflecting real source coverage.
- **Verification** — Bun has no native "confirm only layer X files loaded" flag either. Use a
  small `Bun.Glob`-based verification script (mirroring the existing
  `scripts/find-hidden-dir-tests.ts` pattern) that globs each suffix and asserts every
  discovered file matches its expected layer directory/suffix pair — e.g.
  `scripts/verify-layer-naming.ts` — rather than relying on a flag that doesn't exist.

## Coverage targets

Single coverage floor, enforced by standard tooling — no per-tier CI thresholds. Criticality
(from the inventory) drives *prioritization* — write critical-path tests first — not
enforcement; the CI gate does not need a maintained criticality mapping.

| Layer | Minimum CI floor | Notes |
|---|---|---|
| unit | ≥80% line, ≥80% branch | Critical-path files should reach ≥90%+ via team practice, not a separate CI gate. This repo's `scripts/check-coverage.ts` already enforces an aggregate 90%/89% lines/functions floor via `task test:coverage` — stricter than the 80% default, which is fine (never below the floor, no upper limit on tightening it). Keep the existing stricter gate rather than loosening it to exactly 80%. |
| integration | every named boundary covered | Measured by code path (every Prisma-service method, every external-client method), not line count. |
| smoke | every public route 200/4xx covered | Route coverage across all 5 Hono services' route tables, not code coverage. |
| E2E | every top-5 journey covered | The inventory's 5 user journeys (dev-task→review→patch→merge/deploy, agent provisioning, Slack chat, marketing-site visitor, local HITL bootstrap) — journey coverage, not per-page coverage. |
| content | every command/skill/agent markdown file has at least one structural assertion | Not a % target — presence/absence per file, given ~85+ markdown files. |

**Why a single floor:** per-tier thresholds require a maintained criticality mapping in CI; as
files are added, moved, or reprioritized the mapping decays silently. A single floor enforced by
`lcov`/`check-coverage.ts` avoids that maintenance burden while criticality still directs
planning-time attention (see the inventory's per-item criticality column).

## Speed budgets

Defaults from `${CLAUDE_PLUGIN_ROOT}/skills/speed-budgets/SKILL.md` — this repo does not
tighten them further at this time (no measured baseline yet; Phase 3 may propose tightening
once real timings exist):

| Layer | Per-test 95p | Per-test hard cap | Suite target |
|---|---|---|---|
| Unit (+ content) | <50 ms | <200 ms | <30 s |
| Integration | <2 s | <10 s | <3 min |
| Smoke | <5 s | <15 s | <30 s seq / <60 s full |
| E2E | <30 s | <90 s | <10 min |
| Full PR pipeline | — | — | **<15 min** |
| Canary suite | — | — | not applicable (`deploy_model: direct`) |

A "unit" test exceeding 200ms, or a "smoke" test exceeding 15s, is a mis-layered-test signal
per the speed-budgets rubric — treat the hard cap as a guillotine during Phase 3 migration, not
a guideline.

**Parallelization plan:**

- **Unit+content:** single-process `bun test`, no sharding by default — Bun's runner is fast
  enough for this surface size without it. Revisit only if the suite approaches 30s.
- **Integration:** single shared Postgres container per CI job run; sequential `bun test`
  execution against it (truncate-between-tests keeps this safe without connection-pool
  contention). Add multi-process fan-out only if approaching the 3 min budget.
- **Smoke:** safe to parallelize freely (in-process, no shared external state) if ever needed;
  not required to hit <60s given current surface size.
- **E2E:** Playwright worker sharding — `workers: 4` (`site/`), `workers: 2` (`admin/e2e/` and
  `metrics/e2e/`).
- **Enforcement:** per the speed-budgets skill, add both `timeout-minutes` at the CI-job level
  (suite target × 1.5, rounded up) and native per-test timeouts (`bun test --timeout 200` for
  unit/content, Playwright's `timeout: 90000` for E2E) so drift past a hard cap fails loudly
  instead of silently accumulating after this blueprint is implemented.

## Shared helpers / utilities to build

- **HTTP request builders** — shared auth-header builders per service's auth model: bearer
  token (task-store, mcp-server), dual session-or-bearer (admin's `api-auth.ts` pattern), chat
  service tokens.
- **Test-user / test-agent factories** — `createTestAgent()`, `createTestTask()`,
  `createTestPullRequest()`, `mintTestBearerToken()`, seeded through each service's own
  service-layer methods per the API-first seeding rule above.
- **DB reset helper** — one truncate-all-tables helper per Prisma schema (admin, task-store,
  chat), run in a shared `beforeEach` for every integration suite in that workspace.
- **Prisma test-DB bootstrap helper** — spins up (or connects to) the test Postgres, runs
  `prisma migrate deploy` for the relevant schema, and returns a scoped `PrismaClient` —
  reusable across admin/task-store/chat integration suites.
- **Time freezer** — a `FakeClock` test double per workspace's existing injectable `Clock`
  interface (`agent/src/clock.ts`, `admin/src/clock.ts`, `mcp-server/src/clock.ts`,
  `task-store`'s equivalent) for deterministic time-dependent tests (claim-TTL logic,
  stale-claim reaping, session retention).
- **Recorded-fixture loader** — one shared recorded-fixture-double-loading utility (`loadFixture(name)`) for
  the JSON fixture directories listed in the Local execution architecture table (GitHub, Slack,
  K8s, Google, Okta, Groq/ElevenLabs, Web Push).
- **Injected-exec double** — one shared interface + fake implementation for `gh`/`git`/`helm`/
  `kubectl` shellouts, reused across `scripts/hitl.ts`, `minikube.ts`,
  `agent-workspace-pull.ts`, and the agent's `check-*.ts` family.
- **Playwright auth fixture** — a shared login/session-cookie-injection fixture for
  `admin/e2e/*.e2e.ts` so every admin E2E spec doesn't re-implement login.
- **Content-layer assertion helper** — a shared markdown-frontmatter/section-presence assertion
  utility for `*.content.test.ts`, given ~85+ command/skill/agent markdown files to check.

## Repo configuration

> Without this section, the pipeline above is advisory. With it, CI is the actual merge gate.

### Branch protection (`main`)

Per the flat, repo-agnostic `repo-config` recommendation (this repo is on, or moving toward,
`shipwright-deploy` with the merging account as a ruleset `bypass_actor`):

- **Required PR** — no direct pushes.
- **Required status checks** — every layer-relevant job from the CI shape above:
  `lint / typecheck / test` (job `ci`), `shell`, `site build / brand-lint / smoke` (job
  `site`), `e2e (metrics dashboard)` (job `e2e`), `e2e (admin UI)` (job `admin-e2e`). Docker
  build jobs (`admin-docker-build`, `agent-docker-build`, `metrics-docker-build`) are
  build-validation, not test-layer jobs — include them if desired but they're out of this
  blueprint's scope.
- **Require conversation resolution before merging** — **no.** `check-patch.ts`'s
  `hasUnaddressedFindings()` only re-checks unresolved threads when a qualifying review exists
  at the *current* HEAD commit; a later CI-only fix commit with no fresh review can leave a PR
  permanently stuck on stale unresolved threads nothing in the pipeline ever revisits. The
  ruleset `bypass_actor` bypasses this setting anyway, so it isn't even a safety net for manual
  merges — not worth the risk.
- **Require branches up to date before merging** — **no.** Bypassed by the same
  `bypass_actor`, and has a real cost: every merge into `main` invalidates every open sibling
  PR's "up to date" status under a multi-agent merge cadence, forcing wasted rebases and full
  CI re-runs.
- **Required approving reviews** — **0.** GitHub blocks self-APPROVE via the API;
  `review.md` Step 10 force-downgrades an agent's review of its own PR to `COMMENT` with a
  `Verdict: APPROVE` marker, so a required-review count can never be satisfied by the pipeline
  itself.
- **Enforce on admins** — **no.** The merging account still depends on being a ruleset
  `bypass_actor` for the common self-reviewed-PR case; `enforce_admins: true` would either
  block every automated merge or require permanent bypass-actor status anyway.
- **Canary status check** — does not exist for this repo. `deploy_model: direct` means there is
  no canary CI job to (not) require in the first place — this isn't "excluded from the
  merge-gate," it's simply absent.

### Required secrets

- **`TEST_CANARY_API_KEY`** — **not required.** No canary suite exists under `deploy_model:
  direct`.
- **Recorded-fixture recording credentials** (used only when re-recording fixtures, never in
  normal CI runs — see the deferred recorded-fixture maintenance loop below): one per external
  integration named in the Local execution architecture table — e.g. Groq/ElevenLabs API
  credentials (`agent/src/voice.ts` recordings), a scoped GitHub PAT/App credential, a Slack
  bot token, and Google/Okta OAuth test client secrets. Scope these to a dedicated
  `recorded-fixture-refresh` GitHub Environment, not shared with the CI integration-test run.
- **Test Postgres credentials** — already plain workflow env vars in `ci.yml`
  (`DATABASE_URL_ADMIN_TEST`, `DATABASE_URL_SHIPWRIGHT_TASK_STORE_TEST`,
  `DATABASE_URL_SHIPWRIGHT_CHAT`), pointed at the ephemeral `services: postgres` container —
  not secrets, since the container and its credentials exist only for the duration of the job.

### Required GitHub Environments

**None**, for the deploy pipeline — `deploy_model: direct` explicitly rules out
staging/production GitHub Environments per CLAUDE.md.

The one environment this blueprint does recommend is unrelated to deploy: `recorded-fixture-
refresh` (no required reviewers — the cron runs unattended, restricted to a single
not-yet-built `recorded-fixture-refresh.yml` workflow). This is the recorded-fixture
maintenance-loop pattern from `repo-config/SKILL.md`, and it is explicitly **deferred / not
implemented** — do not build it until the manual, hand-authored-fixture workflow above is
running and tuned. Do not conflate this environment with the deploy pipeline's (absent) staging/
production environments — it exists purely to scope re-recording credentials away from normal
CI.
