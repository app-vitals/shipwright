# Shipwright Agent — Key Files

> Per-file reference table for `admin/src` and `agent/src`, backing the Shipwright agent (artifact **C**). See [agent.md](./agent.md) for the agent's architecture, HTTP surfaces, and data model.

## Key Files

| File | Purpose |
|---|---|
| `admin/src/main.ts` | Standalone admin service entrypoint — runs `prisma migrate deploy`, constructs all services, and mounts health + runtime API + admin CRUD API + admin UI. Dockerfile `ENTRYPOINT`. Mounts `GET /health` (liveness, DB-independent) and `GET /health/ready` (readiness, DB-aware via `checkDbReady()`) so a transient DB blip never triggers a liveness-driven restart but does keep the pod out of Service rotation. Exports helper functions `runMigrations()`, `buildProvisioner()`, `buildDeletionClients()`, and `checkDbReady()` to enable unit testing of env-driven configuration logic and the readiness DB check in isolation from `Bun.serve()` and real Prisma connections; the full `startServer()` integration is exercised via deployed environments and service integration tests. `buildDeletionClients()` independently selects task-store and chat-service provisioning clients for `deleteAgentFully()` based on env vars (URL + admin token for each), orthogonal to K8s provisioning configuration. |
| `admin/src/api.ts` | Runtime API factory `createAgentRuntimeApp()` (OpenAPIHono app with OAS 2.1 route definitions; DI for services). |
| `admin/src/agents-api.ts` | Admin CRUD factory `createAdminApp()`. |
| `admin/src/api-auth.ts` | Combined admin auth middleware (`createAdminAuthMiddleware()`) and env-key parser (`parseAdminApiKeys()`) — bearer check order: env API keys (scope enforcement), then DB token via `agentTokenService`; bearer path does not fall through to session cookie on failure. |
| `admin/src/openapi-schemas.ts` | Zod schemas for the admin and runtime APIs — entity types (Agent, AgentCronJob, AgentTool, AgentToken, AgentPlugin), request bodies, runtime response shapes (AgentConfigResponse, RuntimeError), and common error shapes (Error, Ok). Imported by route migrations (OAS-2.1, OAS-2.2); `z` imported from `@hono/zod-openapi` for `.openapi()` metadata support. |
| `admin/src/admin-ui.ts` | Admin UI factory `createAdminUIApp()` — server-rendered Hono app (login, agent list/detail, Slack/GitHub provisioning, tasks, chat threads, work queue) with POST mutation routes for repos (add/delete), review-author-allowlist and patch-author-allowlist (add/delete), cron jobs, tools, per-agent tokens (create/revoke, via `agentTokenService` — `POST /admin/agents/:id/tokens` and `POST /admin/agents/:id/tokens/:tokenId/revoke`), tasks (release), threads, and messages (including multipart file uploads). Includes `POST /admin/agents` (admin-only: creates self-hosted or provisioned-in-cluster agent), `GET /admin/agents/new` (admin-only: new agent form with type picker, runtime selector, optional review-author-allowlist and patch-author-allowlist textareas, optional AI credentials fields; for in-cluster agents only: optional inline Slack connection (UAP-2.1) and optional inline GitHub auth mode selector (UAP-2.1); Slack/GitHub sections and their form fields are hidden client-side when "Self-hosted" runtime is selected, and the `POST /admin/agents` handler further gates Slack/GitHub provisioning server-side to in-cluster agents only (UAP-5.1) as a defense-in-depth check). On `POST /admin/agents`, the form accepts optional `connectSlack` checkbox, `xoxpToken` (app config token, used once then discarded), `ghAuthMode` radio (skip/pat/app), `ghPat` (personal access token), `githubOrg` (for manifest-flow app creation), `restrictSlackToMembers` checkbox (restricts Slack access to configured agent members only; when checked, the `memberEmails` textarea becomes visible for bulk-adding members), and `memberEmails` textarea (optional, one email per line; emails are best-effort added to the agent's `AgentMember` rows during creation, with duplicates silently ignored) — all of which are ignored when creating a self-hosted agent. When both Slack and GitHub are requested, GitHub PAT storage runs first (synchronous), then Slack's OAuth redirect is returned last, so GH_TOKEN is already in place when the user returns from Slack's callback. Message routes: `POST .../messages/upload` (multipart form; body + optional file; validates attachment size ≤10 MB and MIME type; returns JSON for client-side error handling) and `POST .../messages` (legacy form POST; redirects on completion). Cron job display includes execution history (last run timestamp, outcome, today's run count). Slack provisioning: per-agent connect-slack routes (`POST /admin/agents/:id/connect-slack`, `GET /admin/agents/:id/connect-slack/callback`, `POST /admin/agents/:id/connect-slack/app-token`) let operators provision a Slack connection directly on an already-existing agent; inline Slack connection during agent creation also uses `SlackProvisioningService` (UAP-1.1, UAP-2.1). GitHub provisioning: per-agent connect-github routes (`POST /admin/agents/:id/connect-github`, `GET /admin/agents/:id/connect-github/callback`, `GET /admin/agents/:id/connect-github/installed`) let operators provision a GitHub connection directly on an already-existing agent; inline GitHub auth during agent creation also uses `GithubProvisioningService` (UAP-1.2, UAP-2.1). Legacy entry point `GET /admin/provision` redirects to `GET /admin/agents/new`. Accepts `devAuthEnabled`, `fetchTaskStoreTasks`, `fetchTaskStoreTask`, `releaseTask`, `taskStoreProvisioningClient`, `agentTypeRegistry`, `agentWorkQueueService`, `agentService`, `chatClient` in `AdminUIDeps`; when `devAuthEnabled=true`, registers `GET /admin/dev-login` (dev auto-login). When `fetchTaskStoreTasks` is provided, `GET /admin/tasks` queries tasks and `GET /admin/sessions/:id` queries tasks for a session; without it, both pages render in degraded mode. Additionally, when `fetchTaskStorePrs` is provided (AXR-1.2), `GET /admin/tasks` performs a parallel PR join for each task that has `repo` and `pr` fields populated, fetching linked PR data (blocked, blockedReason, claimedBy, claimedAt, heartbeatAt) and rendering them as data attributes on task rows for future board-UI consumption; the join gracefully degrades on task-store unavailability or missing fetcher, leaving rows without PR data when the join fails. When `fetchTaskStoreTask` is provided, the PR list's `taskId` filter resolves the task (PTL-2.1) and the task detail page fetches the linked PR; without it, both degrade gracefully (PR list renders empty, task detail omits PR section). When `taskStoreProvisioningClient` is provided, per-agent Slack connection provisioning (`POST /admin/agents/:id/connect-slack/app-token`) mints a per-agent task-store token during agent setup, mirroring the K8s provisioning path. When `agentTypeRegistry` is provided (defaults to a disk-backed `AgentTypeRegistry`), the new-agent form (`GET /admin/agents/new`) calls `listTypes()` to populate the agent-type dropdown and validates the selected type before creation via `tryGetManifest(typeName)`. When `agentService` is provided, the admin UI uses it for agent CRUD operations: `listAll()`, `listByIds()`, `searchByName()`, and `listOptions()` for fetching agent lists for dropdowns (e.g., `/admin/agents/new`, `/admin/chat`) and filtering tasks by agent name (e.g., `/admin/tasks?agent=`); plus `create()`, `delete()`, `getDetail()`, and `updateFields()` for managing agent lifecycle via `POST /admin/agents` (self-hosted or provisioned agent creation), `GET /admin/agents/:id` (detail view), and repo-attachment/detachment flows (`POST/DELETE .../repos`), replacing direct Prisma calls with a service layer for consistent data access and enabling agent-management CRUD on the admin UI. When `agentMemberService` includes `listByAgentId()`, the admin UI uses it to fetch agent members on the agent detail page (replaces direct `prisma.agentMember.findMany()` calls), scoped to admins only. When `agentWorkQueueService` is provided, the admin UI composes both work-queue and cron-logs displays into a merged `/admin/agents/:id/queue-activity` page (AXR-3.1). The queue-activity page fetches the accessible agents list (via `resolveAccessibleAgents()` — admin: full fleet; non-admin: AgentMember-scoped) and passes it to `renderQueueActivityPage()` for in-page agent switching (AXR-3.4). When `chatClient` is provided, `GET /admin/chat*` routes access threads and messages; without it, chat routes render in degraded mode. `GET /admin/agents/:id/queue-activity` renders a unified Queue & Activity page with two sections: "Upcoming" displays the agent's latest ranked work-queue snapshot (tasks/PRs across dev-task/review/patch/deploy phases, as last pushed via `POST /agents/:id/work-queue`), and "Past" displays a per-agent cron log across every cron the agent owns — filterable by `cronId`, `outcome` (posted/dm/silent/skipped/error), and `page` query params — sourced from `agentCronRunService.listForAgent()`. The page is linked from both the agents list ("Queue & Activity" button on each row) and the agent detail page's per-cron "Logs" button (which pre-selects that cron via `?cronId=` in the Past section). |
| `admin/src/dev-auth-guard.ts` | `isDevAuthAllowed(env)` — pure predicate over an injected env object (`DevAuthGuardEnv`). Returns `true` only when `ADMIN_DEV_AUTH=true` and `NODE_ENV !== "production"`. Mirrors the `chat-guard.ts` safety pattern. |
| `admin/src/admin-ui-pages.ts` | Page rendering functions (`renderLoginPage`, `renderAgentsPage`, `renderNewLocalAgentPage`, `renderAgentDetailPage`, `renderTasksPage`, `renderTasksBoard`, `renderSessionDetailPage`, `renderPrsPage`, `renderPrDetailPage`, `renderTokensPage`, `renderQueueActivityPage`, `renderChatPage`, `renderChatThreadPage`). `renderNewLocalAgentPage()` includes a helper `runtimeSectionsOnchange()` that returns inline JavaScript to toggle visibility of the Slack/GitHub sections based on runtime selection (in-cluster = visible, self-hosted = hidden); the three section IDs (`restrict-slack-group`, `slack-section`, `github-section`) are rendered with dynamic `style="display:${runtimeSectionsDisplay}"` attributes and onchange handlers that inject the JavaScript via `runtimeSectionsOnchange()` to ensure client-side visibility matches the selected runtime — this gating is complemented by server-side defense-in-depth in `admin-ui.ts`'s `POST /admin/agents` handler (UAP-5.1). The `restrict-slack-group` section is always visible and contains a `restrictSlackToMembers` checkbox; when checked, a `member-emails-fields` textarea becomes visible allowing operators to bulk-add member emails (one per line) at agent creation time. The restricted Slack section also includes an explanatory note warning that if no members are added, the restriction will block all Slack senders until members are configured. `renderTasksPage(tasks, opts, readOnly, timezone, prsByTaskId, view?, now?)` dispatches to one of two layout renderers based on the `view` parameter (AXR-1.3): when `view === "board"`, delegates to `renderTasksBoard()` for the 3-column Kanban layout (Queued / In Progress / Blocked-HITL per TBC-2.1); otherwise (default `"table"`) renders the legacy paginated table. The table view shows task list with a filter form (state, session, repo, source, agent, hitl status dropdowns/inputs) and a paginated table (ID, title, status badge, assignee, session, repo, source, PR link, created time, actions); applies filters as query params (state, session, repo, source, agent, hitl, page) and preserves them in pagination and state-tab links (CTV-4.2); the table view also always carries `view=table` forward in pagination and state-tab links to preserve the table view (TBF-1.1 — bare `/admin/tasks` now defaults to the board per AXR-1.3, so row links into task detail and session detail pages must carry `?from=<current-table-url>` and the table URL itself must include `?view=table` to round-trip back correctly). When `prsByTaskId` is provided (from the `GET /admin/tasks` PR join, AXR-1.2), task rows render with data attributes for the joined PR fields (blocked, blockedReason, claimedBy, claimedAt, heartbeatAt), plumbing these through for board-UI rendering; `GET /public/tasks` passes an empty map so the public board never performs or exposes the PR join. Task detail pages include skip count (when > 0) and last skipped timestamp (when skipCount > 0), and a linked PR section when the task has `repo` and `pr` fields populated — fetched via a live `fetchTaskStorePrs(repo, prNumber)` lookup (failure, absence of the fetcher, or missing task.repo/task.pr renders the page without a PR section). `renderTasksBoard(args)` renders the AXR-1.3 Kanban board layout for `GET /admin/tasks` (default when no `view` param or `view=board`) or explicitly `GET /admin/tasks?view=board` — a 3-column board (Queued / In Progress / Blocked-HITL, rendered per TBC-2.1; the underlying `bucketTaskColumn()` function still supports all 5 possible column values but the default board view omits Claimed and Done, which are accessible via `?view=table` filters instead) bucketed via `bucketTaskColumn()` using task status, hitl flag, blockedBy entries, and PR blocked status, with the same filter form and filter query params as the table view (status, state, session, repo, org, source, agent, hitl, page), but displayed as unlabeled `<div>` cards (task ID, title, status badge, assignee, task age badge via `relativeTime(task.createdAt, now)` when `createdAt` is valid, joined PR blocked badge if applicable) grouped into columns instead of rows (TBC-1.1 — age badge shows relative time with ISO tooltip). The default filter row (visible without disclosure) shows only Org and Repo multiselects (restyled with AXR-1.1's scope-select class and kept independent so org-with-no-repo matches all repos under that org); the remaining filters (status/hitl/session/source/agent) are collapsed under a `<details class="more-filters">` disclosure (AC1). Org and Repo stay as two independent `<select multiple>` controls exactly as on the table view, never merged into a combined scope-pill selector (AC2). Back-links and pagination query params round-trip identically whether the request landed on board or table view, carrying `?view=board` or `?view=table` forward as appropriate. `renderPrsPage` renders the PR list with three state-tabs (Open, Merged, Blocked) and a paginated table (PR #, repo, task link, state badge with optional "Waiting: Blocked" badge for blocked PRs, reviewState badge, review/patch cycles, created time, actions); applies filters as query params (state, reviewState, org, repo, blocked, page — org and repo support multiple selections via URL param arrays; taskId is accepted but ignored as a no-op for backward compatibility, PTL-3.1) and preserves them in pagination links. The filter form includes multi-select dropdowns for both org and repo, populated from the provided suggestions list merged with any active selections. The "Blocked" tab queries with `state=open&blocked=true` to show open PRs that are blocked (PR record has `blocked=true` OR linked task has `status=blocked`); hovering the "Waiting: Blocked" badge shows the `blockedReason` tooltip. `renderPrDetailPage` renders PR metadata: id, repo, PR link, state, reviewState, review/patch cycles, branch, commit, staged flag, claimed-by agent, linked task(s) — fetched via a live `fetchTaskStoreTasks(repo, prNumber)` lookup (PTL-2.3) — status (when found), Blocked flag (when set), `blockedReason` text (when present), skip count (when > 0), and last skipped timestamp (when skipCount > 0). The page gracefully degrades when the fetcher is absent or the lookup fails, rendering without a task section. `renderQueueActivityPage` renders the merged per-agent Queue & Activity page (AXR-3.1): an "Upcoming" section displaying the agent's self-reported ranked work queue (tasks/PRs across dev-task/review/patch/deploy phases, as last pushed via `POST /agents/:id/work-queue`), with a numbered table (rank, type badge, phase badge, item ID+title, age in relative time) sorted oldest-first, or a clear empty state when no snapshot has been pushed yet (agent has no shipwright-loop cron or hasn't ticked since this feature shipped); plus a "Past" section with a filter form (cron dropdown labeled by name/schedule, outcome dropdown: Any/posted/dm/silent/skipped/error) and a weekly-collapse partition (via `partitionCronsForActivityDisplay()`) that separates the shipwright-loop cron (always visible in the primary table) from all other crons (grouped in collapsed `<details>` disclosure blocks, one per cron, preserving insertion order). Within each cron's table (primary or collapsed), a table (outcome badge with title tooltip showing skipReason for skipped runs or error message for failed non-skipped runs, owning cron, start time, duration, item column with distinctly-colored Task/PR badges linked to the dispatched work item ID, token usage, cost, per-model cost breakdown, phase, detail column showing error text if present or skipReason when skipped, with CSS truncation and a title attribute for full text on hover) with pagination mirroring `renderPrsPage`'s pattern (X–Y of Z summary, Prev/Next links preserving active filters); all tables share the same column-header row (CRON_RUN_TABLE_HEAD constant) and the cron-outcome styling helper with the agent detail page's cron rows. The page includes an in-header agent selector (AXR-3.4) — a `<select>` form that navigates to `/admin/agents/{selected-id}/queue-activity` on change, allowing operators to switch between agents without leaving the queue-activity view. The selector is populated from the caller-supplied `agents` array (defaults to `[agent]` for backward compat when omitted). Also exports new interface `CronGroupingInput` (for partitioning crons), and new helper function `partitionCronsForActivityDisplay(crons) → {visibleCronIds, collapsedCronIds}` (pure partition function). Exports `WorkQueueItem` interface (type/id/title/phase/age), `WorkQueueSnapshotItem` interface (computedAt/items), `AgentOption` interface (id, name — for the agent selector dropdown). `renderSessionDetailPage` renders a session summary (stat cards: total tasks, estimated hours, distinct layers), an open/closed tasks summary, a task table sourced from a live `/tasks?session=` fetch (columns: title, status, layer, hours, repo, source), and a distinct dependency list (gracefully degrades when task-store is unavailable or degraded mode is set). Accepts optional `backHref` parameter (defaults to `/admin/tasks`) for the "← Tasks" back link, allowing navigation to return to the originating tasks list or task detail page; back links are validated via `resolveSessionDetailBackHref()` to reject open redirects (protocol-relative, absolute, javascript:, or unrecognized paths). `renderChatPage` renders the thread browser (agent selector, search box, thread list with ID/title/created/view link; gracefully degrades when chat service absent). `renderChatThreadPage` renders a thread detail page with a scrollable message area, sidebar thread list pane, rename form, delete button, and floating send form. Messages render as styled bubbles: user messages on the right with indigo background, assistant messages on the left with green background and markdown support (bold text, inline code), system messages centered with yellow background, and error states (when `errorKind` is set) with red error badges labeled by error kind (cancelled, incomplete, stalled, rate-limited, timeout, upstream). Errored replies with recoverable error kinds (`cancelled`, `incomplete`, `stalled`) also render a Retry button that resends the original user message without UI refresh. Assistant messages with token data display per-message token/cost badges showing input tokens, output tokens, and USD cost. Thread-level aggregated stats (total input/output tokens and total cost) render in the thread header on desktop; on mobile (≤640px), stats and rename/delete actions are hidden from the header but remain accessible via the sidebar drawer. On mobile, the sidebar becomes a CSS-only off-canvas drawer (translateX slide-in animation, dismissible by scrim tap) accessed via a hamburger button in the header; the header is collapsed to ~48px + 16px meta line to keep the message stream above the fold. The drawer uses a checkbox-driven toggle pattern with a scrim overlay, fully styled via CSS and requires no JavaScript beyond viewport-tracking for the iOS keyboard inset. Attachment metadata is shown as an inline badge (📎 filename) when a message carries an attachment (read-only display; no re-download — attachments are ephemeral and dropped after the agent fetches them). The reply form includes an "Attach file" button that opens a file picker (accepts images, PDFs, JSON, text files, and SVG); selected files display a filename preview below the input. Client-side JavaScript handles form submission (multipart upload via the `/messages/upload` endpoint), optimistic message bubble insertion, Retry button clicks (wired via `data-retry-body` attribute), a "thinking…" indicator during polling, server polling (3-second intervals, 90-second timeout), and iOS-specific viewport tracking (mapping visualViewport height to a CSS custom property for safe sticky-composer positioning when the on-screen keyboard shrinks the viewport). Accepts `threads: ChatThread[] | null` and optional `stats?: ThreadStats | null` for thread-level stats. Gracefully degrades when chat service absent. Exports `AgentDetail` interface (agent detail with `selfHosted` boolean flag), `TaskItem` interface for typing tasks displayed on the admin UI, `PrListItem` interface for PR data displayed on PR list/detail pages (fields: id, prNumber, repo, state, reviewState, reviewCycles, patchCycles, mergedAt, branch, commitSha, staged, claimedBy, agentId, createdAt, updatedAt, blocked, blockedReason, skipCount, lastSkippedAt, and others), `CronRunItem` interface for cron run rows on the run-log page, and `AgentOption` interface (for the agent selector dropdown). `renderTokensPage` accepts optional `agents` (agent list for the create-token dropdown), `selectedAgentId` (pre-selects an agent), and `taskStoreBaseUrl` (renders env block in success banner). Also exports `classifyTaskState(task) → "ready" | "in_progress" | "blocked" | "closed"` — pure classifier that assigns UI state-tab buckets to tasks; returns `closed` for terminal statuses, `blocked` for tasks with outstanding `blockedBy` entries (unresolved dependencies or hitl waits) regardless of status (blockedBy check runs before status checks for priority-ordered grouping), `in_progress` for tasks with status `in_progress`/`pr_open`/`approved` and no blockers, and `ready` otherwise. Deterministic single-pass classification used by both the task table and the dependency graph card. Also exports `TaskBoardColumn` type (`"queued" | "claimed" | "in_progress" | "blocked_hitl" | "done"` — 5 possible values), `TASK_BOARD_COLUMNS` array (the 3-column default board definition per TBC-2.1: Queued / In Progress / Blocked-HITL; Claimed and Done are excluded but still valid outputs of `bucketTaskColumn()` for use by other callers), and `bucketTaskColumn(task, prBlocked?) → TaskBoardColumn` — a pure bucketing function (AXR-1.2, the single source of truth for task-to-column resolution; wired into `renderTasksBoard()` in AXR-1.3) that resolves every task to exactly one of 5 possible column values in precedence order: done (terminal statuses), blocked_hitl (task.status="blocked" OR task.blockedBy is non-empty OR task.hitl=true OR the joined PR is blocked), in_progress (status in_progress/pr_open/approved with no blockers), claimed (pending with claimedBy set), or queued (pending without claimedBy, and the fallback for any unrecognized status). Per TBC-2.1, `renderTasksBoard()` renders only the first 3 of these 5 column values (Queued, In Progress, Blocked-HITL). Also exports dependency-graph layout helpers: `DependencyNode` interface (node in a task dependency graph; id, title, status, branch, dependsOn), `DependencyLayout` interface (computed layout positions and canvas size), `DependencyLayoutPosition` interface (x/y pixel coords and depth), `computeDependencyNodes(tasks) → DependencyNode[]` function (extracts participating tasks from the input list and returns them as a flat deterministically-ordered array, filtering for any task that has dependencies or is referenced as a dependency by another task; omits tasks unrelated to dependency edges), and `computeDependencyLayout(nodes) → DependencyLayout` function (pure layered-DAG layout assigning each node a column based on longest-path depth and rows within columns per input order; cycle-safe via memoization and recursion-stack guards; converts abstract depths to pixel positions using fixed-size card dimensions and margins from the approved mockup). |
