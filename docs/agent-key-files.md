| `admin/src/coding/session-alert-sweeper.ts` | `SessionAlertSweeper` — one of the admin service's five background loops (SESH-7.4; see `trial-expiry-sweeper.ts`, `trial-expiry-warning-sweeper.ts`, `account-trial-expiry-sweeper.ts`, and `account-trial-warning-sweeper.ts` for the others), registered as a background pass via the coding `AdminExtension`'s `backgroundPasses` hook during admin boot (in `admin/src/admin-boot.ts`, never inside an app factory) and gated on Web Push being enabled AND `SHIPWRIGHT_TASK_STORE_URL` + `SHIPWRIGHT_TASK_STORE_ADMIN_TOKEN` being set; cadence comes from `SHIPWRIGHT_ADMIN_SESSION_ALERT_INTERVAL_MS` (default 60s). Mirrors `chat/src/stall-reaper.ts`: injected `Clock`, per-session and per-follower `try`/`catch` so one bad row can never abort the sweep, and a counted return value. `tick()` resolves to `{ immediate, reminders, completions, pruned }` and never throws — a failure gathering its inputs (the injected `fetchSessions("waiting"\|"closed")` task-store call, or the `UserNotificationPrefs` read) short-circuits to all-zero counters and sends nothing. `tick()` is deliberately **not** re-entrant: a second call while a sweep is in flight logs and returns all-zero rather than racing it, because the dedup here is a read-then-write across network I/O (`sessionAlertState.findMany()` → `notifySession()` → `upsert`) and two overlapping ticks would both see `lastAlertedAt = null` and both push. (The guard is per-process; multiple admin replicas would need a shared lock.) The admin boot sequence bounds the task-store fetch with `AbortSignal.timeout(SESSION_ALERT_FETCH_TIMEOUT_MS)` (10s) so a hung task-store can't wedge the loop behind that guard, and threads `SHIPWRIGHT_ADMIN_PUSH_MAX_DETAIL` through as `detailLevel` so session pushes honor the operator ceiling instead of silently capping at `"title"`. Per waiting session it materializes auto-follow rows for visible users whose `autoFollowSessions` is true — skipping any session that was already waiting before that user's `autoFollowSince` opt-in (`startedWaitingBefore()`; a null `autoFollowSince` is the "always on" cohort and has no boundary) — then sends one `immediate` push the first time a follower is alerted and at most one `reminder` per later local day once that user's `reminderHourLocal` has passed; per closed session it sends one `completed` push per follower, then deletes that pair's `SessionFollow` + `SessionAlertState` rows so it never fires again. Visibility per follower is resolved at most once per email per tick with `session-scope.ts`: an email on the operator allowlist (`adminAllowedEmails`, the same `SHIPWRIGHT_ADMIN_ALLOWED_EMAILS` list `createAdminUIApp` gates on) scopes to `"all"` via `visibleAgentIdsFor(true, …)` and is alerted without holding any `AgentMember` row; anyone else scopes to their memberships (`visibleAgentIdsFor(false, …)` / `isSessionVisible()`, the rule `admin-ui-session-follow.ts`'s `memberCanSeeSession()` applies). Followers who lost visibility get no push and have their alert-state row pruned. Every per-follower outcome is written through an injected `log` (default `console.log`): one line per push sent (`<kind> → <email> for <slug>: delivered=N pruned=M` — `delivered=0` means the follower never enabled push on any device) and one per follower skipped as not visible, so a follow that never turns into a notification is never silent. Muted follows are skipped. Because `SessionAlertState` stores only a nullable `lastAlertedAt` (deliberately no "kind" column), the alert kind is *derived* by the exported pure helpers `localDateKey(date, tz)`, `localHour(date, tz)`, and `resolveWaitingAlertKind(lastAlertedAt, now, reminderHourLocal, tz)` — no migration required. Also exports `SessionAlertPrismaLike` (the narrow Prisma slice), `SessionAlertStateRow`, `SessionForAlert`, `MembershipLookup`, `AgentReposLookup`, and `SessionAlertSweepResult`. |

When the busy flag is true, the loop detects a prior tick still draining by checking elapsed time from `busySince` (LPF-7.2: busy-stall escalation): if elapsed time exceeds 35 minutes (`BUSY_STALL_THRESHOLD_MS`), the tick is stuck somewhere before dispatch (well past the 30-minute `runner()` timeout ceiling) and will not self-recover, so the skip log escalates to `console.error` (Sentry-eligible) instead of the routine `console.warn`, matching the spin-detection style for alerting. `busySince` is re-baselined at the top of every drain iteration AND again at the top of every dispatch attempt (`runOneAttempt`), so the measured window never spans more than one `runner()` call — without the per-attempt reset, DTW-1.3's auto-resume loop (up to 4 sequential `runner()` calls, ~2 hours, inside a single iteration) would trip the threshold and emit a false "stuck/wedged" error on a healthy dispatch. Every real dispatch reports its own tagged `AgentCronRun` row (scoped to the dispatched phase, part of the shared shipwright-loop cronId), enabling per-phase cost/token attribution even though every invocation shares the same scheduled cron. Ordering the renewal after the ownership gate keeps it from refreshing a claim that now belongs to another agent; a renewal failure stops the resume loop without failing the dispatch.
