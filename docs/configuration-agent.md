### Per-agent fields

| Field | Type | Default | Description |
|---|---|---|---|
| `reviewAuthorAllowlist` | `string[]` | `[]` | GitHub login strings permitted to trigger this agent's review/dev-task work. **Empty means unfiltered** — every authenticated author is allowed. **First exposure per agent (RAM-1.1):** the allowlist gates only an agent's first exposure to a PR — once this agent's own GitHub login has a non-PENDING review on the PR, it keeps reviewing later commits even from a non-allowlisted author, and another agent's review (the shared PR record) never bypasses it. A requested-reviewer PR is also always eligible. If the PR's reviews can't be fetched the allowlist applies (fails closed). Assumes agents use separate GitHub logins. Settable at creation (admin UI create-form field) and editable afterward (admin UI agent-detail page's add/delete rows, or `PATCH /agents/:id`). For local dev, `hitl.ts`'s `SHIPWRIGHT_HITL_AUTHORS` env var is the equivalent — it stays in sync with the persisted record via `PATCH` (see the `SHIPWRIGHT_HITL_AUTHORS` row under [Dev-only](#dev-only)). This was previously named `authorAllowlist`; that column was removed in DBR-2.4. |
| `patchAuthorAllowlist` | `string[]` | `[]` | GitHub login strings naming additional authors whose PRs this agent will treat as patch candidates. **DBR-1.3:** synced live via `agent/src/coding/patch-author-allowlist-ref.ts`. **DBR-1.4:** enforcement is active — `check-patch.ts` adds PRs authored by allowlisted logins to the candidate pool (merged with self-authored, deduplicated by repo/number). Empty allowlist means self-authored-only (additive source, not fail-open). Settable at creation and editable via `PATCH /agents/:id`; not yet surfaced as an admin UI form field. |
| `autoPostReviews` | `boolean` | `true` | **APM-1.3:** the `auto_post_reviews` policy field. Editable via `PATCH /agents/:id` or the admin UI's Agent Policy card. Read by `/shipwright:review` (Step 1 policy read via `GET /agents/:id/config`), then the hardcoded default. |
| `allowSelfReview` | `boolean` | `false` | **APM-1.4:** the `allow_self_review` policy field. Synced live via `agent/src/coding/allow-self-review-ref.ts` (updated every ~60s from `GET /agents/:id/config` by `index.ts`'s `syncConfig()` call). Enforcement is active — `check-deploy.ts` and `check-review.ts` use `readAllowSelfReview()` (check-helpers.ts), which returns the DB value via `allowSelfReviewRef` once synced, else the hardcoded `false`. |
| `minConfidence` | `integer` | `75` | **APM-1.3:** the `min_confidence` policy field. Read by `/shipwright:review`, same read order as `autoPostReviews` above. |
| `maxFindings` | `integer` | `5` | **APM-1.3:** the `max_findings` policy field. Read by `/shipwright:review`, same read order as `autoPostReviews` above. |

### Shipwright platform

| Name | Type | Default | Description |
|---|---|---|---|
| `SHIPWRIGHT_RECONCILER_DELAY_MS` | `number` | `300` (300 ms) | Delay in milliseconds inserted between GitHub API calls in the PR state reconciler's each gh-call-issuing loop (PSR-1.2), spread across every record iteration. When a reconcile pass lists 70+ PR records for checking, this delay spreads their GitHub queries out over ~21 seconds instead of firing them in a sub-second burst, preventing exhaustion of the shared `GH_TOKEN`'s rate limits (confirmed live: tight bursts exhausted the GraphQL limit for ~9 minutes, blocking sibling agents' dispatch work). Production implementations use a real `setTimeout`-backed pause; tests inject a no-op. Env-var-only; read once at process start, allowing runtime tuning for ops without a code change. Recommended range: 200–500 ms depending on the agent's GitHub call concurrency and the limit headroom of the token's plan. |
| `SHIPWRIGHT_RECONCILER_UPDATED_SINCE_WINDOW_MS` | `number` | `21600000` (6h) | Recency window (PSR-1.1) for the PR state reconciler's `updatedSince` filter, applied only to `reconcileReviewState`'s pending-record scan — this pass only re-fetches records updated within this window instead of unconditionally rescanning every record every tick, avoiding the same GraphQL rate-limit exhaustion `SHIPWRIGHT_RECONCILER_DELAY_MS` mitigates. As of RPS-1.1, `reconcilePrState`'s open-record scan (Entry point 1 above) no longer uses this filter — see the module doc comment in `agent/src/coding/pr-state-reconciler.ts` for the rationale. Deliberately wide relative to `SHIPWRIGHT_PR_STATE_RECONCILER_INTERVAL_MS`'s 30-60 minute tick interval: this pass exists specifically to heal a task-store record whose `updatedAt` will never change again once truly stuck by a crash/hang, so the window only needs to survive a missed or delayed tick (restart, deploy) rather than exclude every record that isn't brand-new. `listPostedReviewRecords` (CHU-2.4) is permanently exempt from this filter regardless of window size, and as of RCB-1.1 so is `reconcilePrOpenTasks` (see `SHIPWRIGHT_RECONCILER_PR_OPEN_TASK_BATCH_SIZE` below) — see the module doc comment in `agent/src/coding/pr-state-reconciler.ts`. Env-var-only; read once at process start. |
| `SHIPWRIGHT_RECONCILER_PR_OPEN_TASK_BATCH_SIZE` | `number` | `200` | Per-tick fetch cap (RCB-1.1) for `reconcilePrOpenTasks`'s batch + rotating-offset cursor scan of task-store Tasks with `status:"pr_open"`. Replaces an earlier `updatedSince` recency filter for this one pass specifically: nothing ever bumps a pr_open task's `updatedAt` while it sits waiting on human review, so a PR that took longer than the recency window to merge would permanently fall out of every future scan and never get reconciled — even after merging on GitHub (confirmed live: over a dozen tasks stuck this way after a slow review turnaround). Each call fetches up to this many tasks (paginated in the usual 50-record page) starting at an in-process, module-level rotating offset cursor; when a call's fetch comes up short of the batch size, the cursor wraps back to 0 so the next call restarts from the beginning — a round-robin sweep across ticks that eventually covers the whole list without ever permanently excluding a stuck record. The cursor is process-local (not persisted) and resets to 0 on restart. Env-var-only; read once at process start. |
| `SHIPWRIGHT_RECONCILER_SCOPE_DEGRADED_RETRY_DELAY_MS` | `number` | `1000` (1s) | Bounded pause before `listAllTasksForBranch`'s single retry (RSG-1.2) of a task-store `GET /tasks?repo=&branch=` response that reported `scopeDegraded:true` (RSG-1.1 — set when the calling agent token's own repo-scope resolver call failed, which forces `repos` to `[]` server-side and can silently under-count or zero out real bundle-mate tasks sharing a branch). The BBR-1.1 bundle-mate guard call sites inside `reconcilePrOpenTask`'s direct and branch-fallback paths depend on this count being trustworthy before auto-healing a branch-only PR match; if the retried response is STILL degraded, the true sibling count is treated as unknown and the auto-heal is skipped (same effective outcome as a confirmed `>1` sibling count), logging a message distinct from the existing "N tasks share this branch" skip so the two causes stay distinguishable in practice. A non-degraded response (including a legitimate 0- or 1-task result) never triggers this delay at all. Production uses a real `setTimeout`-backed pause (reusing the same injected `delay` dep PSR-1.2 already threads through this file); tests inject a no-op. Env-var-only; read once at process start. |
| `SHIPWRIGHT_AGENT_PR_CENSUS_ENABLED` | `"true"` \| `"false"` | `true` (unset or anything other than `"false"`) | Kill switch for POM-4.1's repo-wide merged-PR census sweep (`agent/src/coding/pr-census.ts`, `runPrCensus`), the fifth independent pass on the PR-state-reconciler's SAME tick (see `SHIPWRIGHT_PR_STATE_RECONCILER_INTERVAL_MS` above and the Step 5b doc comment in `agent/src/index.ts`). When explicitly set to `"false"` (case-insensitive), the pass short-circuits before touching any repo — zero `gh`/task-store calls of any kind. Each tick, per scoped repo: fetches the repo's incremental-search cursor (`GET /prs/census/cursor`, POM-1.1) — a `null` cursor (the repo's first run) issues zero `gh` calls and zero census entries rather than backfilling full history (full historical backfill is handled separately by POB-1.1's one-time `agent/scripts/backfill-pr-origin.ts` script); otherwise issues exactly one `gh pr list --state merged --search "merged:>=<cursor>"` call (GitHub's Search API, 30 req/min — distinct from the general 5000/hr REST limit), classifies each result via the label-free `classifyPrOrigin()` precedence (`shipwright -> ci -> dependency_bot -> human -> unknown`, where the `shipwright` check matches against the repo's task-store tasks with a non-null `pr` field rather than any GitHub label, and wins over an author login/branch name that would otherwise say `ci`/`dependency_bot`), and `POST`s the classified batch to `POST /prs/census` in chunks of at most 200 entries, ascending by `mergedAt`. A per-repo failure (cursor fetch, `gh` call, task list, or POST) is caught and logged without stopping the other scoped repos in the same tick. Read once at deps-construction time (`buildProductionDeps` in `pr-census.ts`), mirroring this file's other env-var-read-once-at-deps-construction-time passes. |
| `SHIPWRIGHT_AGENT_PR_CENSUS_INTERVAL_MS` | `number` | unset — no separate throttle beyond the shared reconciler tick interval | Optional additional throttle for the census sweep above, layered on top of (not a replacement for) `SHIPWRIGHT_PR_STATE_RECONCILER_INTERVAL_MS`'s own tick cadence — useful for running the census pass less often than the other four passes on the same tick, e.g. because the Search API's 30 req/min limit is tighter than the general REST limit the other passes share. When set, `runPrCensus` tracks the wall-clock time of its own last completed tick (in-process module state, mirroring `pr-state-reconciler.ts`'s `prOpenTasksCursor` precedent — resets on process restart) and skips the entire tick, including the cursor/GitHub calls for every scoped repo, until at least this many milliseconds have elapsed since that last completed tick. Time is read via an injected `Clock` (never `Date.now()` directly) so the throttle stays unit-testable. When unset, every reconciler tick runs the census pass with no additional throttling. Env-var-only; read once at deps-construction time. |

### Loop orchestrator

| Name | Type | Default | Description |
|---|---|---|---|
| `SHIPWRIGHT_LOOP_EMPTY_BACKOFF_MS` | `number` | `300000` (5 min) | Duration in milliseconds for the empty-queue backoff window (SKT-2.2). When the loop has collected zero candidates for `SHIPWRIGHT_LOOP_EMPTY_BACKOFF_ATTEMPTS` consecutive ticks, the next tick skips all candidate collection (no GitHub calls, no task-store queries) and remains idle for this duration before resuming normal work selection — a low-cost way to reduce redundant external API calls when the queue is genuinely drained. Read fresh on every tick (never cached) so an operator's env change takes effect on the very next tick without an agent restart. See also `SHIPWRIGHT_LOOP_EMPTY_BACKOFF_ATTEMPTS`. Env-var-only. |
| `SHIPWRIGHT_LOOP_EMPTY_BACKOFF_ATTEMPTS` | `number` | `3` | Consecutive empty ticks required to trigger the empty-queue backoff window (SKT-2.2). When the loop collects zero candidates for this many ticks in a row, the following tick enters backoff (skips all candidate collection) for `SHIPWRIGHT_LOOP_EMPTY_BACKOFF_MS` milliseconds. A tick that dispatches at least one item resets this counter immediately — real work interrupts a backoff on the very next tick. Read fresh on every tick (never cached) so an operator's env change takes effect on the very next tick without an agent restart. See also `SHIPWRIGHT_LOOP_EMPTY_BACKOFF_MS`. Env-var-only. |
| `SHIPWRIGHT_LOOP_<PHASE>_ALT_COMMAND` / `SHIPWRIGHT_LOOP_<PHASE>_ALT_SHARE` | `string` / `number` (0-100) | unset / `0` | Per-run command variant switch (DTA-1.3). `<PHASE>` is `DEV_TASK`, `PLAN`, `REVIEW`, `PATCH` or `DEPLOY`. With a positive share, that percentage of the phase's dispatches (chosen at random per run) use the alternate slash command (e.g. `/shipwright:merge`) instead of the default. The alternate must be a `/shipwright:<name>` command with a matching file in the plugin; an invalid value falls back to the default with a warning. The variant used (`default` / `alternate`) is recorded per run as `commandVariant` on the cron run record. Unset or `0` leaves behavior unchanged. |
| `SHIPWRIGHT_AGENT_AUTONOMOUS_PLAN_SESSION_ENABLED` | `"true"` | unset (off) | Code-level kill switch for the autonomous plan-session loop phase (PDR-4.1). Must be exactly `"true"` to take effect. This is ANDed with the `shipwright-plan` cron toggle in the specialty manifest — **both** must be on before `loop-orchestrator.ts` collects or dispatches a single plan candidate; with this unset, the loop's behavior is byte-for-byte what it was before the phase existed. When enabled, the loop queries the task store for `?kind=prd&status=pending` tasks (`agent/src/coding/check-plan.ts`), pre-claims the winning task via the same atomic `POST /tasks/{id}/claim` the dev-task phase uses, and dispatches `/shipwright:plan-session {repo} {session} --autonomous {task-id}`. Read fresh on every tick (never cached) so an operator's env change takes effect on the very next tick without an agent restart. Env-var-only. |

| `SHIPWRIGHT_MCP_SERVER_TOKEN` | `string` | — | Bearer token required on every inbound request to the MCP server (except `/health`). Read by `mcp-server/src/main.ts` at startup; the service fails closed and refuses to start if unset. Prevents unauthorized access to the tool proxy surface, since the server holds `SHIPWRIGHT_TASK_STORE_TOKEN` and proxies authenticated calls into the task store on behalf of any connected client. Bearer auth uses constant-time comparison to avoid side-channel leaks. Env-var-only (secret). |
| `METRICS_ADMIN_APP_URL` | `string` | `""` | The reverse of `METRICS_DASHBOARD_URL`: base URL of the admin console for the metrics **dashboard** toolbar's Agents/Tasks/PRs links. Defaults to empty (same-host relative links, suitable for single-host ingress). Set to an absolute URL when the admin console runs on a different origin than the metrics dashboard (e.g. in local `task stack`: `http://localhost:3001`), otherwise those links 404 on the metrics origin. Distinct from the server-to-server `METRICS_ADMIN_URL`. |
