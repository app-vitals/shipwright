# Shipwright Agent — Operations

> Coding half. The platform half is the vendored snapshot [`docs/platform/agent-ops.md`](./platform/agent-ops.md), sourced from `app-vitals/agent`.

> Tool authorization/narrowing, default system crons, environment configuration, and baked marketplaces for the Shipwright agent (artifact **C**). See [agent.md](./agent.md) for the agent's architecture, HTTP surfaces, and data model.

## Default system crons

Every new agent is seeded with the system crons declared by its **specialty's defaults** — for the `coding` type the source of truth is the `crons` array in [`admin/src/coding/coding-specialty-defaults.ts`](../admin/src/coding/coding-specialty-defaults.ts) (fourteen crons), supplied through the coding admin extension's `specialtyDefaults()` hook; the platform consults that hook first and falls back to a specialty manifest only for types without extension defaults. The defaults are reconciled onto each agent at startup via `POST /agents/:id/crons/reconcile`. Reconciliation uses a two-pass strategy: Pass 1 creates or updates each system cron entry (preserving existing IDs for FK stability), recording each into a name → id map. Pass 2 resolves parent/child links by looking up parent cron names in the map and setting `parentCronId` on declared child crons, clearing any existing `parentCronId` back to `null` when an entry no longer declares a resolvable `parentCron` — self-healing the link on every agent boot in both directions with no manual migration. Three are **enabled by default** (`shipwright-dev-task`, `shipwright-review`, `shipwright-patch`); the rest are opt-in (toggle in the admin UI). System crons reject modifications to `schedule`, `prompt`, and `preCheck` via the API, but enabled-only PATCH requests are allowed to toggle the cron (see `docs/platform/agent-api-ops.md`) — they are otherwise kept in sync with the specialty defaults' cron definitions via the reconciliation process. All run `silent` (they post to Slack only on a result worth surfacing, or on error). Some carry a `preCheck` script whose stdout becomes the actual prompt, so a cron only spends a Claude turn when there is real work ready.

The five pipeline crons (`shipwright-plan`, `shipwright-dev-task`, `shipwright-review`,
`shipwright-patch`, `shipwright-deploy`) are **loop-driven, item-addressed executors, not
self-discovering standalone crons.** They are linked as child crons of `shipwright-loop` (via
`parentCronId`), which is the sole supported driver for these five phases: its in-process
candidate providers (`agent/src/coding/check-plan.ts`, `check-dev-task.ts`, `check-review.ts`,
`check-patch.ts`, `check-deploy.ts`) select a winning candidate each tick and
`loop-orchestrator.ts` dispatches the matching command with an explicit task id or
`org/repo#number` embedded in the prompt. None of the five commands scans for its own work —
each responds `[silent]` and exits immediately if invoked with no target.
This means a standalone pipeline cron (`shipwright-loop` disabled) is **silently inert**: its
stored prompt (e.g. `/shipwright:dev-task`) carries no target, so every tick dispatches, goes
`[silent]`, and does nothing. See [migration.md](./migration.md) for the breaking-change
note and the fix (enable `shipwright-loop`).

| `shipwright-loop` | `* * * * *` (every minute) | off | Internal: dispatches enabled pipeline phases (dev-task, plan, review, patch, deploy — `plan` additionally requires `SHIPWRIGHT_AGENT_AUTONOMOUS_PLAN_SESSION_ENABLED`, see its row above) in a single multi-step drain-until-dry run. It's available to wire in per-agent as a [custom cron](./extending.md#custom-cron-jobs-for-scheduled-automation) using the schedule/prompt/preCheck documented in [`docs/site-docs-freshness.md`](./site-docs-freshness.md).

## Multi-repo scoping via `resolveScopedRepos`

`shipwright-docs-freshness` and `shipwright-test-readiness` precheck scripts filter the filesystem-scanned repo list down to the agent's configured `repos[]` via the `resolveScopedRepos` helper (defined in `plugins/shipwright/scripts/check-helpers.ts`). This ensures that a repo cloned locally but absent from the agent's configuration is **excluded from output**, even if it would otherwise qualify (e.g., it has source changes or stale test-readiness artifacts).

`resolveScopedRepos` resolves this intersection by:

1. Fetching the agent's config via `GET /agents/{id}/config` (requires `SHIPWRIGHT_API_URL`, `SHIPWRIGHT_AGENT_ID`, `SHIPWRIGHT_AGENT_API_KEY` env vars).
2. Reading the `repos[]` field from the response.
3. Intersecting it with the filesystem-scanned repo list (local clones in `repos/` or `SHIPWRIGHT_REPOS_DIR`).
4. Returning only repos present in both lists.

**Fail-closed behavior:** If any of the three env vars are unset, or if the config fetch fails, `resolveScopedRepos` returns an empty list. This surfaces as the precheck's existing "no work this tick" result (exit 1, no output) rather than crashing or silently falling back to the unfiltered scan. The assumption is that an agent cannot qualify work until it can confirm its own identity and scoping — missing config is safer to treat as having nothing to do than to guess.

## PR origin census sweep

POM-4.1's repo-wide merged-PR origin census (`agent/src/coding/pr-census.ts`, `runPrCensus`) is not a standalone cron — it's a fifth independent pass on the existing PR-state-reconciler's tick (see `SHIPWRIGHT_PR_STATE_RECONCILER_INTERVAL_MS` in [configuration-agent.md](./configuration-agent.md#metrics--admin--chat--task-store-services)), reinstating visibility into merged PRs the pipeline never claims directly — e.g. a human merging their own PR without ever invoking `/shipwright:review`, or a dependency-bot PR merged untouched.

Each tick, per scoped repo, the sweep reads the repo's incremental search-window cursor (`GET /prs/census/cursor`, POM-1.1 — the max `mergedAt` among rows with a non-null `origin`). **A `null` cursor (the repo's first run) issues zero `gh`/task-store calls for that repo**, rather than backfilling full PR history — full backfill for historical PRs before origin-tracking was deployed is handled separately by POB-1.1's `agent/scripts/backfill-pr-origin.ts` CLI script. The cursor is derived server-side, not written explicitly, so the very next tick after the first shipwright-origin PR lands for that repo naturally sees a real cursor.

Otherwise, the sweep issues exactly **one `gh pr list --state merged --search "merged:>=<cursor>"` call per scoped repo per tick** — GitHub's Search API (30 req/min, distinct from the general 5000/hr REST limit) — classifies each result via the `classifyPrOrigin()` precedence (including the `is_bot` and label signals) (see [metrics.md](./metrics.md#origin-classification-rules)), and `POST`s the classified batch to `/prs/census` in chunks of at most 200 entries. A per-repo failure is caught, logged, and does not stop the other scoped repos in the same tick.

Configured via `SHIPWRIGHT_AGENT_PR_CENSUS_ENABLED` (kill switch) and `SHIPWRIGHT_AGENT_PR_CENSUS_INTERVAL_MS` (optional additional throttle beyond the shared reconciler tick cadence) — see [configuration-agent.md](./configuration-agent.md#metrics--admin--chat--task-store-services) for the full reference; not duplicated here.
